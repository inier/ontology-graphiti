# ADR-055: 统一查询服务 (QueryService)

## 状态
已采纳

## 上下文

当前 ODAP 存在 5 条独立的图谱查询路径：

1. **SelfCorrectingOrchestrator (v1)**: 正则硬编码路由，完全不查询图谱
2. **DomainSwarm (OODA)**: 仅在 Orient 阶段调用 `retrieve_rag_context()`
3. **IntelligenceAgent (ReAct)**: 调用 `retrieve_rag_context()` + SKILL_CATALOG
4. **UserCognitionEngine**: `KnowledgeNavigator` 与 `GraphManager` 接口断裂，实际无法工作
5. **frontend_compat API**: 直接调用 `graph_manager.search()`

问题：
- 意图识别重复实现 4 次，且两个 IntentRecognizer 定义了不同的意图枚举
- KnowledgeNavigator 期望的接口（get_neighbors / get_related_entities / get_node_properties）与 GraphManager 实际方法完全不匹配
- 所有查询方法返回 List[Dict]，无结构化类型
- Agent 可直接调用 graph_manager.add_entity()，无安全边界
- GraphManager 缺少 get_neighbors() / traverse() 等图遍历方法

阿里巴巴 UModel 项目提供了成熟的解决方案：
- **Query First**: 所有读取走 QueryService，禁止散落的域读取端点
- **Query Surface**: `.umodel` / `.entity` / `.topo` 三种查询源
- **Agent Safe**: 默认只读，写工具需显式启用
- **Architecture Guard**: 自动化测试强制执行边界规则

## 决策

借鉴 UModel 的 Query Surface 设计模式，在 ODAP 内部构建统一的 QueryService：

1. **定义四种查询源**：`.schema`（OMS 类型定义）、`.entity`（运行时实体）、`.topo`（拓扑关系）、`.temporal`（双时态数据，ODAP 独有）
2. **新建 `odap/infra/query/` 模块**：实现 QueryService + Parser + Source 抽象
3. **为 GraphManager 补充图遍历方法**：`get_neighbors()` / `traverse()`
4. **通过 OpenHarness Tool 接口注册查询工具**：Agent 统一走 QueryService
5. **实现架构守卫**：pytest 测试强制执行 Query First 规则

### 与 OpenHarness 的集成

QueryService 通过 OpenHarness 的 Tool 接口注册为 Agent 可用工具：
- 查询工具（query_schema / query_entity / query_topo / query_temporal）标记为 `safety="read"`
- 写操作工具（write_entity / write_relation）通过 PreToolUse Hook 调用 OPA 校验
- OpenHarness Swarm Coordinator 中的三 Agent 统一使用 QueryService 工具

### 实施路径

| 阶段 | 内容 | 风险 |
|------|------|------|
| Phase 1 | 新建 QueryService，不破坏现有代码 | 低 |
| Phase 2 | Agent 统一走 QueryService，废弃分散路径 | 中 |
| Phase 3 | MCP Server 集成，外部 Agent 通过标准协议访问 | 低 |

## 后果

**正面**：
- 消除 5 条分散查询路径，统一为 1 个入口
- 修复 KnowledgeNavigator 与 GraphManager 的接口断裂
- Agent 获得结构化查询结果（QueryResult 而非 List[Dict]）
- 实现 Agent Safe 默认只读，写操作需 OPA 审批
- 架构守卫防止未来再次出现查询路径分散

**负面**：
- 现有 Agent 需要逐步迁移到 QueryService
- GraphManager 需要补充 get_neighbors() / traverse() 方法
- 查询语法解析器需要持续维护

## 可逆性
高。QueryService 是新增模块，不修改现有代码。可通过配置开关切换新旧路径。

## 2026-06-06 状态修正：Action Type 与 Skill 分层原则

随着 Phase 11 中 FR-034（Action Type 一等公民）的落地，QueryService 抽象中需要明确"Action Type = 业务接口"与"Skill = 工程实现"的职责分层。本节作为 ADR-055 的状态修正，补充该分层原则的最终决策。

### 1. 核心分层定义

| 抽象 | 定位 | 暴露面 | 复用性 |
|------|------|--------|--------|
| **Action Type** | 业务接口 | 面向用户 / Agent / 外部系统 | 与领域语义绑定，不跨业务复用 |
| **Skill** | 工程实现 | 面向内部执行器 / Skill Registry | 跨业务复用，跨 Action Type 共享 |

- **Action Type 引用 Skill ID**（绑定关系，ActionType.linked_skill_id 强制非空）
- **Skill 不反向依赖 Action Type**（Skill 只关心参数 → 结果，不知道被谁调用）
- 这种"单向依赖 + 静态绑定"避免了 N:M 调用的复杂编排，且符合"接口稳定、实现可换"的工程实践

### 2. 边界关系

```
┌────────────────────────────────────────────────────────┐
│  ActionType (业务接口)                                  │
│  ┌─────────────────────────────────────────────────┐  │
│  │  id: assign-mission                             │  │
│  │  object_types: [Unit]                           │  │
│  │  parameters: { unit_id, mission_id }            │  │
│  │  linked_skill_id: validate-mission              │──┼──┐
│  │  linked_skill_id: persist-mission-log           │──┼──┤ 绑定
│  │  opa_policy_ref: action.assign-mission.policy   │  │  │
│  └─────────────────────────────────────────────────┘  │  │
└────────────────────────────────────────────────────────┘
                                                          │
        ┌─────────────────────────────────────────────────┘
        ▼
┌────────────────────────────────────────────────────────┐
│  Skill (工程实现)                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │  id: validate-mission                           │  │
│  │  handler: validate_mission_handler              │  │
│  │  input_schema: { unit_id, mission_id }          │  │
│  │  output_schema: { valid: bool, errors: [...] }  │  │
│  │  (无 ActionType 引用，禁止 import 上层)         │  │
│  └─────────────────────────────────────────────────┘  │
│  ┌─────────────────────────────────────────────────┐  │
│  │  id: persist-mission-log                        │  │
│  │  handler: persist_mission_log_handler           │  │
│  └─────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

**关键约束**：
- `ActionType.linked_skill_id` 字段强制非空（创建校验），确保"单一事实来源"：业务逻辑只能通过 ActionType 暴露，Skill 永远是具体实现
- Skill 的输入/输出 schema 由 Skill 自己定义（与 ActionType.parameters 解耦），允许 Skill 内部使用更丰富的数据结构
- ActionType 允许绑定多个 Skill（按 `step` 顺序执行），用于"校验 → 持久化 → 通知"等场景

### 3. ODAP 中的实际例子

#### 例子 A：`assign-mission` Action Type（业务语义：分配任务给单元）

```python
# ActionType 业务接口定义
ActionType(
    name="assign-mission",
    object_types=["Unit"],
    parameters={
        "type": "object",
        "properties": {
            "unit_id": {"type": "string"},
            "mission_id": {"type": "string"},
            "priority": {"type": "integer", "minimum": 1, "maximum": 5}
        },
        "required": ["unit_id", "mission_id"]
    },
    return_type="object",
    side_effects=["update_unit_status", "write_mission_log", "notify_commander"],
    opa_policy_ref="action.assign-mission.policy"
)
# 绑定到两个 Skill（按 step 顺序执行）：
#   step 1: validate-mission  (校验单元状态、任务合法性)
#   step 2: persist-mission-log  (持久化任务记录 + 审计)
```

#### 例子 B：`decommission-equipment` Action Type（业务语义：退役装备）

```python
ActionType(
    name="decommission-equipment",
    object_types=["Equipment"],
    parameters={
        "type": "object",
        "properties": {
            "equipment_id": {"type": "string"},
            "reason": {"type": "string"},
            "replacement_id": {"type": "string", "nullable": true}
        },
        "required": ["equipment_id", "reason"]
    },
    return_type="void",
    side_effects=["update_equipment_status", "archive_maintenance_records"],
    opa_policy_ref="action.decommission-equipment.policy"
)
# 绑定到两个 Skill：
#   step 1: validate-state  (校验装备当前状态允许退役)
#   step 2: update-status  (更新状态为 DECOMMISSIONED + 归档维护记录)
```

### 4. 分层带来的好处

1. **可复用性**：同一 Skill 可被多个 Action Type 绑定。例如 `validate-state` Skill 既可被 `decommission-equipment` 绑定，也可被 `transfer-equipment`、`repair-equipment` 等 Action Type 复用，实现"一次实现、多处使用"。
2. **业务清晰**：ActionType 是面向用户/Agent 的"业务接口契约"，参数、返回、副作用都有明确定义；Skill 是工程实现，可独立升级（不影响 ActionType 契约）。
3. **多租户场景下 Skill 共享**：在 SaaS 多租户场景下，平台层维护一个共享 Skill 库，每个租户/工作空间只需定义自己的 ActionType（绑定到平台共享的 Skill），大幅降低重复开发。
4. **可测试性**：Skill 单独测试（输入→输出），ActionType 单独测试（权限 + 业务契约），互不依赖。
5. **可演进性**：未来 Skill 实现可热替换（例如从 LLM 切换到规则引擎），不影响 ActionType 接口。

### 5. 权限与审计的分层边界

| 阶段 | 执行主体 | 校验内容 | 审计写入 |
|------|----------|----------|----------|
| **ActionType 写入时**（preconditions） | OPA 策略引擎 | ABAC 四维（Subject/Action/Resource/Environment）+ 数据分类级别 | 写"action_authorization"审计记录（含 allow/deny 决策） |
| **Skill 执行时**（runtime） | Skill 自身 handler | 业务参数合法性、原子性 | 写"action_execution"审计记录（duration、结果、错误） |

清晰的分层边界避免了职责重叠：
- OPA 只回答"用户 X 是否能调用 Action Y"（write-time check）
- Skill 只回答"这个参数组合能否正确执行业务逻辑"（runtime check）
- 审计日志统一通过 `unified_audit.py` 写入，但带不同 `event_type` 区分授权和执行

### 6. 架构守卫（Architecture Guard）

为防止后续重构中破坏该分层，新增以下静态检查（由 `tests/unit/test_architecture_guard.py` 强制执行）：

1. `Skill` 类的源码中**禁止** import `ActionType` 模块（反之亦然）
2. `Skill` handler 的参数 schema 中**禁止**出现 `action_type_id` / `linked_action` 字段
3. `ActionType` 创建时 `linked_skill_id` **必须**非空（None 拒绝）
4. CI 中 `grep -r "from odap.*action" odap/tools/` 必须为空（Skill 不得 import Action 模块）

### 7. 决策影响

- Phase 11 M2 中 `SkillBackedExecutor`（T382）严格遵循此分层：`execute()` 只接收 `ActionType` 和参数，不感知 Skill 注册表的实现细节
- 未来 Phase 12 若引入"Skill 链式编排"（一个 Skill 触发另一个 Skill），需重新评估该分层是否仍适用（当前决策：**不允许 Skill 互相调用**，必须经过 ActionType 中转）

### 8. 相关决策

- ADR-022（模拟数仓与统一查询服务）：规定所有读取走 QueryService，本节补充"ActionType 与 Skill 的执行边界"
- ADR-024（本体驱动分析核心架构）：明确 ActionType 是本体的"一等公民"
- ADR-051（闭环反馈机制）：闭环中 Action 执行结果回写时，同样遵循 ActionType→Skill 的分层

---

**结论**：本节将 ADR-055 的状态从"提议"提升为"已采纳"，并明确 ActionType（业务接口）↔ Skill（工程实现）的单向依赖分层。后续 Phase 12+ 的所有相关实现必须遵循本节定义的边界与守卫规则。
