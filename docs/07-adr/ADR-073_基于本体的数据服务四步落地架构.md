# ADR-073: 基于本体的数据服务四步落地架构

## Status

**Accepted** (2026-07-30)

## Context

ODAP 项目已经建立了本体设计器、语义管理套件（USL）、推演引擎和部分 API 服务，但这些能力分散在不同的模块中，缺乏统一的对外视图和清晰的演进路线。为了构建完整的"建 → 见 → 演 → 用"本体价值链，需要一个统一的架构决策来对齐现有资产，规划新增能力，并明确与已有设计（ADR-055/072）的关系。

## Decision

我们决定采用**"四步法 + 语义检索服务总线"**的架构来落地基于本体的数据服务。

### 1. 核心架构：四步法

| 阶段 | 核心能力 | 现有资产 | 状态 |
|---|---|---|---|
| **建本体** | 手动+AI 混合建模 | Ontology Designer、Hyper-Extract 链路（TemplateEngine、ValidationEngine）、USL OL 流水线 | 主干在，SP1（HE 真实启用）和 SP2（OL 6 层）待落地 |
| **见本体** | 图谱探查（编辑态/探查态分离） | `OntologyGraphPage`（Sigma.js）、`graph_viewer`、USL 候选双写 | 基础可跑；需强化权限分离和候选态过滤 |
| **演本体** | 微观推演 + 宏观孪生 | `biz/simulation/`（DeductionEngine、DecisionRecommendation）、`sandbox` 隔离 | 模块齐全，代码实现（非空桩），需扩展双时态标记 |
| **用本体** | API/SDK/MCP 开放 | 现有路由、ObjectService、MCP 桥（`openharness_bridge`） | 需建立统一门面和检索服务总线 |

### 2. 关键设计决策

#### 2.1 语义检索服务总线（Semantic Retrieval Service Bus）

这是"用本体"阶段的核心新增架构，同时服务 AI Agent 和 BI 工具。

**路由形态（三层架构）**：
- **统一检索层**：`POST /api/semantic-retrieval/query` — 简单场景，引擎自动路由
- **分项检索层**：`POST /api/semantic-retrieval/{chain|nl|mdl|graph|metric}` — 精确场景
- **混合检索层**：`POST /api/semantic-retrieval/hybrid` — 复杂场景，支持 `components: [{type, params}]` 链式编排

**与 ADR-055 / ADR-072 的关系**：
- 本 ADR 是 **ADR-055（统一查询服务）的超集实现**：ADR-055 仅定义了跨源检索，本 ADR 将其扩展为包含链式推理、自然语言推理、指标查询的完整总线。
- 本 ADR 是 **ADR-072（推理服务契约）的消费者扩展**：ADR-072 定义了推理引擎的内部契约，本 ADR 定义了对外暴露的 RESTful API。
- **后续行动**：将 ADR-055 和 ADR-072 的状态更新为 `superseded-by ADR-073`。

#### 2.2 MDL/DSL 策略

- **禁止新发明 DSL**。复用：
  1.  Hyper-Extract 的 YAML 模板语法（用于结构化推理）
  2.  UModel 的 `.umodel` / `.entity` / `.topo` 语法（参考 ADR-055）
  3.  OPA Rego 语法（用于规则推理）

#### 2.3 推演数据双时态隔离

- 推演产出的数据**不直接写入正式实例层**，而是：
  - 存储于独立的 `simulation_scenarios` SQLite 表
  - 推演结果作为 Neo4j 中带 `scenario_id` 属性和 `valid=false` 标签的节点/边
  - 默认查询（`见本体`）过滤掉 `valid=false` 的数据
  - 推演完成后，用户可通过"采纳"操作将结果提升为正式数据（状态变更为 `valid=true`）

#### 2.4 权限与可见性

- **编辑态**：面向开发者，可修改 TBox/ABox 结构
- **探查态**：面向业务人员，只读访问，默认过滤候选态（USL__Candidate）和无效态（`valid=false`）数据

### 3. 术语定义（参考 CONTEXT.md）

- **本体 (Ontology)** = TBox（结构） + ABox（实例），不包含 USL
- **USL (Unified Semantic Layer)** = 独立的横向语义规范总线，贯穿四步
- **语义检索服务总线** = 用本体阶段的核心服务，三层架构

## Consequences

### 正面影响
- **统一入口**：AI Agent 和 BI 工具通过统一的 `SemanticRetrievalService` 获取数据，避免了三套查询系统并行的混乱。
- **复用优先**：所有新增能力均基于现有资产扩展（如复用 HE YAML、UModel 语法），降低了维护成本。
- **渐进式落地**：四步对应现有 SP 序列（006/007 等），不需要新建平行分支。

### 负面影响与缓解
- **复杂度增加**：混合检索层的编排逻辑较复杂，需要完善的测试覆盖（缓解：复用 `pipeline_service` 的编排机制）。
- **数据一致性**：推演双时态隔离增加了数据管理复杂度（缓解：提供显式的"采纳/回滚"操作和审计日志）。
- **ADR 债务**：ADR-055/072 需要标记为被取代（缓解：在后续 PR 中逐步更新）。

## Considered Options

1.  **单一大路由方案**：将所有检索能力塞进 `/api/reasoning/retrieve`，通过 `mode` 参数区分。
    *   **拒绝原因**：违反单一职责原则，单 endpoint 承担过多职责，难以维护和扩展。
2.  **独立 SDK 包方案**：新建 `odap-ontology-sdk` 独立仓库。
    *   **拒绝原因**：增加了部署和维护负担，与"单体优先"原则（ADR-046）冲突。
3.  **双时态直接融合方案**：推演结果直接写入 ABox，仅用时间戳区分。
    *   **拒绝原因**：会污染正式数据层，增加查询复杂度，且回滚操作代价极大。
