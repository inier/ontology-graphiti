# ADR-086: 概念缺口回路（四信号源汇聚 heat 缺口池 + 人工裁决晋升复用审批飞轮 + side-channel 回调闭环）

## Status
**已接受（2026-10-07）。落地情况（诚实注记，规则 12/14）：设计于 2026-10-07 获用户批准（spec：[docs/superpowers/specs/2026-10-07-concept-gap-loop-design.md](../superpowers/specs/2026-10-07-concept-gap-loop-design.md)）；T1–T8 已以 TDD 实现，6 个 gap 单测文件（storage/emitter/promote/wiring/routes/loop_acceptance）+ 菜单 seed/迁移单测全绿。当前代码仅处于 staged 状态，**待用户 git commit**；dev 容器手验（spec §7 第 2 项）与整分支 stashed-HEAD 回归终审（spec §7 第 4 项）仍为待办。本 ADR 不宣称"已上线"或"已在生产验证"。**

> 触发来源：ODAP 语义层运行时持续产生「概念缺口」信号——用户问到了本体里没有的词、术语归一未命中、QA 兜底回答"未找到相关信息"——但这些信号**全部只落在 logger 里**，无聚合、无回路，本体化石化速度不可见。
> 借鉴边界：参考 **BeModel concept-gap-loop**——借**模式**（运行时"未答"信号聚合 → heat 排序 → 人工裁决 → 晋升复用治理链 → 回调闭环，验收标准"同一个问题下次能答上"），**不借栈**（不引入其任何依赖/存储/服务）。
> 关联：ADR-061（Semantic Admin Suite 独立业务域，gap_pool 为其第 10 个子服务）；ADR-084（open/typed 双层事实模型，同样复用 candidate 审批飞轮）；AGENTS.md 规则 2（服务层返回 dict）/ 规则 3（HTTPException 透传）/ 规则 6（routes→services→storage）/ 规则 8（SQLite 无连接池）/ 规则 9（真实 tmp_path 测试）/ 规则 12（文档同步）/ 规则 14（失败显式、兜底可观测、测试执行真实函数体）。

## Context

### 现状（证据见 spec §1 + 本轮代码勘验）

四类运行时"未答"信号散落在既有显式失败/丢弃分支中，各自只打日志，无任何聚合点：

1. **term_resolve_miss**：`biz/semantic_admin/usl_manager/services/usl_term_resolver.py:113/123` — `canonical_of` 未命中返回 `None`，调用方各自处理。
2. **nl_query_unanswered**：`biz/core/ontology/semantic_retrieval/impl/nl_engine.py:68` — NL 查询 USL 归因 miss 直接 `return None`。
3. **qa_unanswered**：`biz/data/qa/qa_engine.py:1322`（兜底"未找到相关信息"分支）——**唯一 qa_unanswered 发射点**（实发在 `:1324`）。
4. **mapping_failure**：`biz/data/qa/pipeline/understanding/intent_recognizer.py:163`（归一化未命中本体集合的候选被丢弃，防幻觉但不留痕）——**唯一 mapping_failure 发射点**（实发在 `:165`）。spec 勘验修正：`chain_engine.py:130` 的 degraded 属**基础设施降级**而非概念缺口，**不接入**缺口池（保持池内信号纯语义）。

### 问题陈述

后果是**本体化石化的速度不可见**：运营无法知道哪些高频词缺定义、补没补上、补上后是否真的能答。BeModel 概念缺口回路给出的验收标准是「**同一个问题下次能答上**」——本 ADR 把这条标准落成接口与回路验收测试（`test_gap_loop_acceptance.py`），而非口号。

## Decisions

### D1. 独立 `gap_pool` 子服务，不扩展 candidate_store

新建 `apps/api/odap/biz/semantic_admin/gap_pool/`（semantic_admin 第 10 个子服务），标准 7 层目录（models/storage/services/api）。**缺口 ≠ 候选**：candidate 有审批语义与 10 状态机，缺口是运行时信号聚合，生命周期不同。严格 routes→services→storage 调用链（规则 6），服务层返回 `Dict[str, Any]`（规则 2），路由层 `except HTTPException: raise` 透传（规则 3）。

### D2. 同步 emitter 收敛点，绝不 raise、绝不阻塞主响应（规则 14 可观测兜底）

`gap_pool/services/gap_emitter.py` 的 `report_gap_signal` 是四类信号源的**唯一同步收敛点**，信号源侧惰性 import（避免循环依赖），接线点只加一行 emitter 调用、不改原分支返回值语义。emitter 内部任何异常 → `logger.warning` + 模块级 `_emit_failures` 计数（经 `GET /stats` 暴露，**重启归零**，如实登记为取舍而非持久化指标），**绝不 raise**——缺口信号丢失不应拖垮问答/检索主路径。这不是静默兜底：失败有 warning 日志 + 可查询计数，可观测、可测试、可审计（规则 14.2/14.3）。GapService 采用惰性单例，构造失败不写长生命周期缓存（规则 14.5）。

### D3. 数据模型：heat 聚合 + scope 隔离 + occurrence 截断

`gap_pool/models/gap.py` 的 `ConceptGap` dataclass：

- 聚合键 = `expression` 原文（strip）+ `scope_key = "{workspace_id}::{domain_id}"`，唯一索引去重；scope 隔离避免跨 workspace 串味。
- `heat` 每次 signal +1（含首次，`UPDATE ... SET heat=heat+1` 原子累加）；`sources` 仅保留**最近 50 条** occurrence（防无界增长），`source_counts` 存全量计数（计数不丢）。
- `GapStatus`（open/promoted/adopted/rejected）与 `GapSignalSource`（term_resolve_miss/mapping_failure/qa_unanswered/nl_query_unanswered）均为 `(str, Enum)` 双继承。
- 闭环字段：`promoted_candidate_id` / `resolved_term_id` / `dismiss_reason`。
- 状态机：`open → promoted → adopted | rejected`；`open → rejected`（dismiss）；**`rejected` + 新信号 → 回 `open`，heat 续累**（"再次被问" = 上次裁决没覆盖真实需求）。
- 存储表 = **`concept_gaps`**（`gap_pool/storage/sqlite_gap_storage.py:41`）。**如实登记**：该表**不带** semantic_admin 其余 12 张表的 `sa_` 前缀（沿用 spec 锁定的表名，规则 8：每次 connect/close、JSON TEXT 列、ISO 时间字符串）。

### D4. 人工裁决 promote/dismiss；晋升**复用既有审批飞轮**，不新造审批

`gap_service.promote` → `candidate_store.create_candidate_from_gap`（传播 `source_type='concept_gap'`、`source_ref=gap.id`、`source_text=expression` 等既有字段，不改 candidate 表结构），之后质量闸/两级审批/writeback **全部走既有流程零改动**；幂等——已晋升的 gap 再次 promote 返回 `already_promoted`，不重复建候选。`dismiss`（带 reason）→ rejected。**采不采永远人决定，AI 只聚合**。

### D5. side-channel 回调闭环 `on_candidate_resolved`

`biz/semantic_admin/usl_writeback/services/writeback_service.py:115` 消费 GapService：writeback 成功 → `on_candidate_resolved(candidate_id, 'adopted', term_id)`；审批驳回 → `on_candidate_resolved(candidate_id, 'rejected')`。回调**无匹配 gap 时 no-op、绝不 raise**（side-channel 不得反向拖垮写回主流程）；writeback **失败不改 gap 状态**（保持 promoted + 既有 status 页显式展示失败，规则 14 失败显式）。闭环状态以既有流程终态为准，**不猜**。

### D6. 诚实的 resolve-check 与 stats（不假装、不造数）

- `resolve_check`：term 类缺口用 `UslTermResolver.canonical_of` 现场判定；**非 term 类缺口如实返回 `resolvable=False`**（"不假装能判定"），detail 说明判定途径。
- `stats`：`total` / `by_status` / `by_source` / `emit_failures` / `top_heat` / `adoption_rate = adopted/(adopted+rejected)`——**分母为 0 时返回 `None`，不造数**；所有指标从真实记录计算，无比例推断。

### D7. API 面：`/api/semantic-admin/gaps` 6 端点

`gap_pool/api/routes.py`，prefix `/api/semantic-admin/gaps`，已注册 `apps/api/odap/web/router_registry.py:176,391`（生产入口生效，规则：新增路由必须注册）：

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| GET | `/` | get_current_user | 分页列表，过滤 status/source/workspace_id，默认 heat 降序 |
| GET | `/stats` | get_current_user | 统计（**声明顺序在 `/{gap_id}` 之前**，防止被路径参数吞掉） |
| GET | `/{gap_id}` | get_current_user | 详情（sources 时间线、状态、晋升/采纳关联） |
| POST | `/{gap_id}/promote` | **verify_semantic_writer** | 晋升为候选（D4，幂等） |
| POST | `/{gap_id}/dismiss` | **verify_semantic_writer** | 驳回（body 带 reason） |
| GET | `/{gap_id}/resolve-check` | get_current_user | 现场可解析性判定（D6） |

### D8. 前端三页 + 菜单接入

`apps/web/src/modules/semantic-admin/`：`services/gapApi.ts` + 3 页面——`GapPoolPage`（列表，路由 `/semantic-admin/gaps`）、`GapDetailPage`（`/semantic-admin/gaps/:id`）、`GapStatsPage`（`/semantic-admin/gaps/stats`）。菜单项 `menu:build:semantic:gaps`（概念缺口）+ `menu:build:semantic:gap-stats`（缺口统计），挂在 建本体→语义管理 下；走菜单 seed 权威源 `biz/platform/menu_config/seeds/seed_four_steps.py` + 既有 DB 迁移脚本 `migrations/add_gap_pool_menu.py`（规避 seed 幂等 skip 陷阱）。运营可见性是回路成立的前提。

## Alternatives Considered

1. **扩展 candidate_store 承载缺口信号**：被否。缺口是运行时信号聚合（heat/scope/occurrence 语义），candidate 是待治理术语（审批语义 + 10 状态机），生命周期与消费方不同；混装会污染审批池。改为独立 gap_pool 子服务 + 晋升时经 `create_candidate_from_gap` 桥接。
2. **异步队列/后台线程 emitter**：被否。同步直调 + 异常吞为可观测计数已满足"绝不阻塞主响应"，且无新基础设施（队列/线程生命周期管理）；SQLite 单写者在信号量级下足够。occurrence 全量留存与跨 workspace 合并视图列为非目标。
3. **AI 自动晋升（免人工裁决）**：被否。违反"采不采永远人决定"的锁定决策；自动晋升会把噪声信号灌进审批飞轮，放大人工分诊成本。
4. **照搬 BeModel 栈**：被否。只借模式不借栈（同 ADR-084/085 借鉴边界惯例），不引入外部依赖，全部落在既有 SQLite/FastAPI/React 栈内。
5. **在写回主流程内同步更新 gap 状态（而非 side-channel 回调）**：被否。写回失败不应连带缺口回路故障，且 gap 更新失败不得反向拖垮 writeback；side-channel + no-op + 绝不 raise 是最小耦合。

## Consequences

**正面**：本体化石化速度从"不可见"变为可运营——heat 排序直指高频缺定义词；"同一个问题下次能答上"从口号固化为回路验收测试（G-g）；晋升复用既有审批飞轮，零新增审批路径；四信号源接线只加一行调用不改原分支语义，blast radius 小；stats 全字段真实来源，无伪绿 KPI（对齐 ADR-084 D2 度量诚实化精神）。

**负面/风险（如实登记）**：
- **`emit_failures` 重启归零**：内存计数非持久化，进程重启后历史失败数丢失。取舍：该指标是"当前是否有系统性发射故障"的运维信号而非业务 KPI，持久化收益低于复杂度；warning 日志仍留有痕迹。
- **occurrence 截断 50 条**：超出的 occurrence 明细不保留（`source_counts` 全量计数不丢）；审计级追溯需查日志。
- **resolve-check 对非 term 类缺口语义弱**：如实返回 `resolvable=False`，不假装能判定——这意味着 NL query 类缺口的"补上了没有"需人工判断或等子项目 2（语义漂移检测）承接。
- **表名不合 `sa_` 前缀约定**：`concept_gaps` 与 semantic_admin 其余 12 张 `sa_` 表命名不一致，已在 DESIGN.md §5.1 如实登记；不改名（spec 锁定 + 已有测试/迁移引用）。
- **信号纯语义边界**：基础设施降级（如 chain_engine stepper 不可用）**不入池**，缺口池统计不反映基础设施故障——这是刻意的纯度约束，运维信号走 ADR-064 可观测性基线。
- **`canonical_of` 的发信 blast radius 大于 term_resolve_miss 单点**：TERM_RESOLVE_MISS 信号内嵌在 `usl_term_resolver.canonical_of()` 的"未命中"分支里，而该方法除缺口回路的读侧判定外，还被两处**写路径**复用——`candidate_store/services/entity_resolution.py:73/110/111`（候选实体批量归并聚类，逐项两两调用）与 `data/knowledge_base/services/knowledge_base_service.py:375`（KB 写入前的类型归一）。这意味着这两条链路在正常业务处理中也会持续向缺口池发射 TERM_RESOLVE_MISS，heat 增长并非只来自用户问答未命中。取舍：**登记不改**——(a) 写路径归一未命中本身即是"该词缺 USL 定义"的合法语义缺口（对齐 ADR-084 S3），(b) entity_resolution 的两两聚类产生的噪声缺口可由人工 dismiss，(c) 收敛发信点会侵入 usl_manager 语义、超出本期范围。运维解读 heat 时需知晓此来源构成。
- **resolve-check 读侧不发信（终审 M1 回归守卫）**：`canonical_of()` 新增 `emit: bool = True` 形参；`gap_service.resolve_check()` 以 `emit=False` 调用，确保只读判定端点绝不触发 heat+1 / 已 dismiss 缺口复活。回归测试见 `test_gap_wiring.py::test_term_resolver_emit_false_suppresses` 与 `test_gap_promote.py::test_resolve_check_is_read_only_no_signal`。

## 可逆性

**高**。gap_pool 是纯新增子服务：四信号源接线各只有一行惰性 import 的 emitter 调用，删除即回退，原分支返回值语义未变；side-channel 回调（writeback_service 一处调用）删除即回退；`concept_gaps` 为独立 SQLite 表，不与既有表发生外键/迁移耦合；前端三页与菜单项独立可摘除；晋升产生的 candidate 走既有流程，其生命周期不依赖 gap_pool 存续。逆转不留残留状态。
