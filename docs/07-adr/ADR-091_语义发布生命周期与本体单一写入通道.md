# ADR-091: 语义发布生命周期与本体单一写入通道

## Status

**提议（2026-10-28 提交，设计待复审）**

> 设计基线：[`docs/superpowers/specs/2026-10-28-semantic-layer-workbench-design.md`](../superpowers/specs/2026-10-28-semantic-layer-workbench-design.md)。复审通过后由 `superpowers:writing-plans` 拆分 P0–P5 实施计划；本 ADR 的状态随实施推进同步更新。
>
> 关联：ADR-068（本体 3+1 分层）、ADR-073（四步数据服务架构）、ADR-079（LLM 三层治理，§7 领域归属禁止命名反推）、ADR-080（ontology 门面与 C1–C4 分层契约）、ADR-083（图谱软删除）、ADR-084/085（写路径不变量与 SHACL 校验）、ADR-086/090（缺口回路与 promote 路由，"采不采永远人决定"）、ADR-058（RBAC 菜单）。

## Context

### 现状证据

统一业务语义（USL）与本体（Ontology）是平台的两条主干，但两者都缺少治理闭环的必要结构：

| # | 现状 | 证据 | 后果 |
|---|------|------|------|
| 1 | USL 六张工作表无 `status`/`version`/`revision` | `apps/api/odap/biz/semantic_admin/usl_manager/storage/sqlite_usl_storage.py:91-207` | 无法区分草案与已发布；无乐观锁；无法回滚 |
| 2 | USL 直接 CRUD 写入即生效 | `usl_manager/api/routes.py` 写接口 | 编辑中的内容立即成为消费方可读事实 |
| 3 | QA 只按 `domain_code` 取域 | `biz/data/qa/pipeline/query_pipeline.py:58-88` | 未发布语义参与问答 |
| 4 | SHACL 直接读 `usl_cardinalities`/`usl_disjoint_pairs` | `biz/core/ontology/design/engine/shacl/shape_generator.py` | 未发布约束进入校验 |
| 5 | 本体 TBox 至少有五条写入路径 | 人工路由 / AI 工具 / USL 写回 / HE 抽取 / 感知链路 | 权限、审计、版本、校验各自为政 |
| 6 | 本体写路由只依赖 `get_current_user` | `biz/core/ontology/ontology_api/api/routes.py` 写路由 | "没有权限不能编辑"尚未在服务端成立 |
| 7 | AI 助手写工具直接调用 `OntologyService.create/update/delete_*` | `biz/core/assistant/plugins/ai_assistant/tools/write_tools.py:146-598` | AI 可绕过审批、审计、版本直接改 TBox |
| 8 | USL 写回按 `USL__{code}` 命名自动建本体，关系缺端点时降级为 ObjectType | `semantic_admin/usl_writeback/impl/graphiti_writeback_adapter.py:112-136, 442-479` | 违反 ADR-079 §7 与规则 14 |
| 9 | HE 导入直接写本体，逐项异常仅 warning | `biz/data/hyper_extract/services/extract_service.py:1276-1305` | 部分失败不可见 |
| 10 | 感知链路无绑定本体时回退 `oms.create_object_type` | `biz/data/perception/hub.py:209-263` | 未绑定本体的类型静默写入 |
| 11 | 语义地图查看端渲染原始 JSON，后端无分页/过滤/邻居扩展 | `web/.../SemanticMapPage.tsx`；`biz/data/semantic_map/api/routes.py:66-177` | 大图不可探查 |
| 12 | 图谱组件选中态内部自持 | `web/.../GraphView.tsx`、`GraphCanvas.tsx` | 图谱、卡片、详情无法联动 |

### 问题陈述

1. **没有发布态**：USL 的"定义 → 审核 → 发布"只完成到审核写回，写回即消费。需求中的"审核通过进入发布状态，已发布语义用于构建本体、作为数据标准、作为数据提取门控"无法表达。
2. **没有单一写入通道**：五条路径各自实现权限、校验、审计、OMS 同步。修一处漏四处；AI 与抽取链路可绕过人工门。
3. **没有统一工作面**：看（图谱/卡片/表格）、改、审、发分散在多个页面；探查与编辑不是模式，而是不同页面，权限也没有在服务端收口。

### 已确认的边界

- USL 直接 CRUD **保留**，语义收敛为"编辑草案"；发布必须走审核。
- USL **不纳入**本体特有构造（Action/Process/Rule/Function/Indicator）。
- 不存在"只读工作台 + 编辑工作台"两套产品；只有一个工作台，探查/编辑是模式 + 服务端权限。
- AI 在**任何权限下**都不直接写入；只产提案。

## Decisions

### D1. USL 是业务语义的唯一权威源

业务术语、同义词、属性规格、层级、基数、不相交约束只在 USL 定义一次。本体构建、数据标准、抽取门控、QA、SHACL 均从 USL 发布包取语义，不各存一份。

### D2. 工作表即草案，发布版本是不可变快照

- `usl_domains`/`usl_terms`/`usl_hierarchies`/`usl_property_specs`/`usl_disjoint_pairs`/`usl_cardinalities` 继续作为**当前草案**存储，现有 CRUD、候选写回、质量闸无需改表即可工作。
- 发布时生成一条 `usl_domain_versions.snapshot_json`（`usl-package-v1`），保存整个 domain package；不复制六张 `*_published` 表，避免双份真值与迁移面爆炸。
- 消费方只读 `PublishedUslView`（解析 `usl_domains.published_version_id` → 快照），不读工作表。

### D3. 生命周期状态机

```
draft ──submit──→ pending_review ──approve──→ published ──deprecate──→ deprecated
  ↑                     │
  └──reject/request_changes──┘
```

- `draft`：工作表可编辑，不进入消费。
- `pending_review`：变更集冻结；审核基于提交时 diff 快照（`submitted_content_hash`），不基于活表。
- `published`：不可变；`usl_domains.published_version_id` 指向它；一个 domain 同时最多一个 `PUBLISHED`，旧版标 `SUPERSEDED`。
- `deprecated`：不再允许新投影/新抽取会话选择；已固定版本的消费者继续可用，直到显式升级。
- 版本只在发布时创建，不存在 `DRAFT` 版本。

### D4. 直接 CRUD 保留，但只写草案

现有 USL 写接口语义改为"编辑草案"，不触发发布、不影响消费。这是兼容性决策：不打断现有运营习惯，发布门单独叠加。

### D5. 三层保存模型

| 层 | 触发 | 写入对象 | 审核 | 影响消费 |
|----|------|---------|------|---------|
| L1 自动保存 | 600ms 防抖 / 失焦 / Ctrl+S | 草案行（原子 UPDATE + `revision`） | 否 | 否 |
| L2 变更集 | 编辑会话自动创建 / 手动 | `usl_change_requests` + `usl_change_items` | 否（draft） | 否 |
| L3 发布 | 提交 → 审核 → 发布 | `usl_domain_versions` + 指针 | 是 | 是 |

- **L1 只做单行校验**（类型、长度、枚举、canonical 字符集、必填）。跨行约束（无环、两端存在、互斥）在提交审核、发布事务、用户主动"校验"三个时点执行。
- **变更项不是暂存区**：item 与草案写入同一 SQLite 事务；`usl_change_items` 是已应用变更的差异/审计日志。
- **同字段连续编辑合并**：同一 `(change_request_id, entity_kind, entity_id, field_path)` 在配置窗口（默认 300s）内更新末条 item 的 `after_json`、累加 `edit_count`、保留最早 `before_json`；撤销按 `before_json` 恢复。
- **复合操作原子**：一次批量请求在同一个 SQLite 事务内校验并应用全部 items，任一失败全部不落。
- **撤销**：前端保留 50 个会话级操作；服务端每条 item 存 `inverse_json`，按逆操作 + 当前 `revision` 应用。跨变更集只允许撤销未提交的 draft。发布后"撤销" = 新建回滚变更集，不是时间倒流。

### D6. 变更集是审核与发布的最小单元

`usl_change_requests` 状态：`draft → pending_review → approved / rejected / request_changes → merged`。一个 domain 同时最多一个 `pending_review`。复合操作（如"新建关系 + 两端对象 + 基数"）必须是同一个 `atomic=true` 变更集，避免半成品进入审核。

### D7. 发布必须人工审核，AI 只做预审

- 延续 ADR-086/090 的"采不采永远人决定"：`ai_review_json` 只作证据，不自动批准/驳回/合并。
- AI 预审 = 确定性检查（引用、环、重复、类型）+ LLM 语义建议（存疑项、术语冲突、定义含糊），输出结构化 JSON 与 `doubtful[]`。
- 四眼原则：`created_by != reviewer`；创建者自批返回 403。
- 审核期间草案被并发修改 → `USL_REVIEW_BASE_MISMATCH_409`，要求 rebase，不自动合并。

### D8. 单向流：USL 发布版 → 本体草案 → 本体稳定版 → 消费

- 本体可消费 USL 发布包生成**投影提案**，写入本体草案；不自动提交稳定版。
- 本体不得反写 USL；反向只允许产生缺口/提案信号。
- 已发布本体不因上游新版本自动变更；升级是显式提案（漂移可见，人工决定）。

### D9. `OntologyWriteGateway` 是唯一写入通道

所有来源统一为"产提案 → 网关校验并应用"：

| 来源 | `origin` | 目标 |
|------|----------|------|
| 人工设计器 | `human` | 保存即应用（保留即时体验），增加 revision/审计 |
| AI 助手 | `ai` | 只产 `OntologyChangeProposal`，人工确认后应用 |
| USL 投影 | `usl` | 显式 `ontology_id` + `version_id`；不自动建本体 |
| HE 抽取 | `extract` | HITL 预览后应用；逐项错误显式返回 |
| 感知链路 | `perception` | 必须绑定本体；无绑定则产提案，不写 OMS |

网关职责唯一实现一次：权限（`ontology.draft.write`）、revision 乐观锁、提案落库、类型校验、OMS/存储同步、审计、事件。

### D10. AI 无直接写入

- 配置 `ai.write_mode` 只有 `proposal` 一个合法值；出现其他值**启动失败**。
- AI 继承调用者身份与权限，不服务账户、不拓宽 scope。
- 提案记录 `origin=ai`、`model`、`prompt_version`、`confidence`、`evidence`；应用时二次确认，审计同时保留 `origin=ai` 与 `applied_by=<user>`。
- 删除 `write_tools.py` 中的直写工具并从工具注册表移除，防止模型误用。

### D11. 一个工作台、四工作区、三视图、模式门

- 路由 `/semantic-admin/workbench`；四工作区：定义 / 审核 / 发布 / 探查；三视图：图谱 / 卡片墙 / 表格；共享选中态 + URL 深链。
- `mode=explore` 默认只读，编辑控件**不渲染**（不是禁用）；`mode=edit` 进入前查 `GET /workbench/capabilities`，无 `semantic.draft.write` 显示明确拒绝原因。
- 服务端每个写接口独立鉴权；前端能力查询只是 UX，不是安全边界。
- `embed=1` 只是同一工作台的布局开关（强制只读），不授权、不新建页面/API。

### D12. USL 不含本体特有构造

USL 治理业务语义（对象/关系/属性 + 约束）；Action/Process/Rule/Function/Indicator 由本体设计器维护。避免 USL 演化成第二个本体。

### D13. RDF 是序列化格式，不是审批通道

- 导出只允许 `published` 版本；草案导出需显式 `?draft=true` + `semantic.draft.write`，文件头标注 `DRAFT`。
- 导入解析 → 结构校验 → 与草案 diff → 生成 `draft` 变更集；**永不直接发布**。冲突项标 `doubtful`。
- 只映射 USL 治理对象；不承诺内部 ID、审计字段、审批状态的往返保真。

### D14. 消费方固定版本

所有消费入口显式携带或解析 `usl_version_id`：本体投影、抽取门控、QA、SHACL、语义检索/MCP。未发布域显式报错或标记 `unpublished`，不静默读草案。SHACL 缓存键改为 `(domain_code, version_id, content_hash)`。

### D15. 并发用 revision + 409；撤销用操作日志

每行 `revision INTEGER NOT NULL DEFAULT 1`，更新必须带 `expected_revision`。变更集记录 `base_content_hash`，批准时不一致返回 409 要求 rebase。不做 CRDT/实时协同。发布版本不可回卷，回滚 = 新版本。

### D16. 迁移与消费切换必须显式

- `scripts/migrate_usl_publish_v1.py`：建表/加列幂等；回填 `revision=1`；对每个未发布域构建 `v1` 快照并写 `bootstrap_publish` 事件；校验失败非 0 退出；不自动切换消费模式。
- `USL_CONSUMPTION_MODE=published|draft`，默认 `published`；`draft` 仅用于迁移期回退，启动 `warning` 并在 `/health`、指标暴露；非法值启动失败。开关是显式配置，不是静默兜底。
- 域删除保留已发布快照与发布事件（`DEPRECATED`/`archived`），不物理级联。

### D17. 架构守卫 C5

新增 import-linter 契约 `C5-ontology-single-write-channel`：

- `type=forbidden`；`source_modules=["odap.biz","odap.infra"]`（排除 `odap.biz.core.ontology` 内部包）；`forbidden_modules=["odap.biz.core.ontology.ontology_api.services.ontology_service"]`；`allow_indirect_imports=true`。
- `public.py` 只导出 `OntologyWriteGateway` 与读服务，不导出 `OntologyService` 写方法。
- 迁移期以 `ignore_imports` 逐条登记 W1–W5 调用点，只减不增；清零后 `lint-imports` 期望 `5 kept, 0 broken`。

## Consequences

### 正面

- 业务语义第一次有"发布"这个可审计、可回滚（以新版本形式）、可固定版本的边界。
- 本体写入从五条自由路径收敛为一个网关；权限、审计、版本、校验只实现一次，AI 与抽取链路不再有旁路。
- 工作台把"看、改、审、发"放在同一份事实上，消除页面间口径漂移。
- 未发布语义不再静默进入 QA/SHACL/抽取，规则 14 的"失败显式"在语义链路上成立。

### 代价与取舍

- 新增表与列、迁移脚本、`PublishedUslView` 解析层；短期内有双读模式（`published|draft`）的复杂度。
- 发布是人工门，运营节奏会比"改完即生效"慢；这是需求明确要求的人工确认，不是性能问题。
- 五条写入路径迁移期需要债账（`ignore_imports` + `origin=legacy` 告警），不能一次清零。
- 快照是整包 JSON，域特别大时单行体积较大；首版接受，后续若超阈值再评估分片（不在本 ADR 范围）。

### 风险与缓解

| 风险 | 缓解 |
|------|------|
| 迁移误把草稿发布为 v1 | dry-run + 校验 + 备份；失败非 0 退出；不自动执行 |
| 发布事务部分成功 | 单事务 + 指针最后更新；失败整体回滚；测试覆盖中途失败 |
| 消费方忘记固定版本 | 契约强制 `usl_version_id`；未带版本按"最新发布"解析并在响应回填实际版本 |
| 网关成为新单点 | 网关只做编排，校验/存储仍由现有服务承担；按来源可单独回退 |
| AI 提案质量低 | 提案必须人工应用；预审标注存疑项；工具注册表移除直写工具 |

## Alternatives Considered

1. **只修补现有页面（不做发布态/网关）**：改动小，但无法回答"审核通过进入发布状态""AI 在什么权限下能写""本体只有一条通道"，且五条写路径继续分叉。否决。
2. **两套工作台（只读 + 编辑）**：与用户明确的"整体就一个工作台"冲突，也会产生两份状态与两套权限判断。否决，改为模式 + 服务端权限。
3. **把 USL 扩展成完整本体（含 Action/Process 等）**：会让 USL 变成第二个本体，业务语义与结构建模混在一起。否决，保持 USL 只治理业务语义。
4. **AI 按权限直写、仅事后审计**：与 ADR-079/086/090 的人工门原则冲突，且不可逆变更风险高。否决，AI 只产提案。
5. **发布时复制六张 `*_published` 表**：查询直观，但双份真值、双份迁移、双份一致性维护。否决，采用整包快照 + 视图。

## Compliance

| 规则 | 落地 |
|------|------|
| 规则 1 路由注册 | 新路由注册至 `apps/api/odap/web/app.py`（P1/P2） |
| 规则 2 服务层返回 dict | 所有新服务返回 `{"status","code","message"}`，不抛 HTTPException |
| 规则 3 路由透传 | 新路由 `except HTTPException: raise` |
| 规则 6 调用链 | `routes → services → impl/storage`，不跨层 |
| 规则 9 测试 | 新模块同步 `tests/unit/`；存储测试用 `tmp_path` 真实 SQLite |
| 规则 12 文档同步 | 见设计 §6：架构四步文档、spec 003/007、模块 README/DESIGN、agents.md、本索引 |
| 规则 13 临时文件 | 迁移输出写 `apps/api/data/migrations/`；不写项目根 |
| 规则 14 失败显式 | 取消 `USL__` 命名反推、关系降级 ObjectType、HE 吞异常、感知 OMS 回退；AI 只提案；L1 非法值不落库 |
