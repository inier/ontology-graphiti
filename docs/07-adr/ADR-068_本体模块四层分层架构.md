# ADR-068: 本体模块四层分层架构（Design → Construction → Reasoning → Application）

## Status
Proposed

## Context

当前本体模块 `odap/biz/core/ontology/` 名义上拆分为 `design/`（本体设计）和 `application/`（本体应用）两个子系统，实际存在以下结构性问题：

### 问题清单

1. **构建逻辑混在设计层**: `design/services/` 的 12 个服务中有 4 个属于构建阶段（`build_service`, `ingest_service`, `pipeline_service`, `qa_ontology_builder`），与版本管理、编辑锁等设计阶段服务平级混放。`ingestion_split/` 是独立的平行摄入系统，与 `design/ingestion/` 功能重叠。

2. **推理服务完全缺失**: 项目无 `reasoning/` 目录。类型推断在 `assistant/rules/`，意图识别在 `cognition/impl/`，一致性校验在 `health/` —— 4 个模块分散管理，无统一推理入口。

3. **三套 AI 助手并存**: `ontology/assistant/`（T063, AG-UI）、`core/assistant/`（plugin, tool-call）、`core/chat/`（unified, ADR-050）三套协议不同、功能重叠。

4. **application/ 职责膨胀**: 7 个子模块覆盖元数据、运行时、服务化、数据集成、查询、智能体，缺乏内部契约，实际是「不属于 design 就塞 application」的垃圾桶模式。

5. **8 个游离模块**: `branch/`, `conflict/`, `computed/`, `inheritance/`, `view/`, `action/`, `cold_start/`, `extraction/` 在 `ontology/` 顶层无明确层级归属。

### 业务驱动

本体领域存在天然的四阶段生命周期：**Design（设计 schema）→ Build（构建实例）→ Reason（推理分析）→ Apply（应用交互）**。当前两层架构没有覆盖 Build 和 Reason 两个关键中间层，导致代码归属混乱、能力发现困难、扩展耦合严重。

## Decision

将本体模块重组为**四层分层架构**，每层通过 Contract（Frozen Dataclass Views）对外暴露能力：

```
odap/biz/core/ontology/
├── design/          # L1: 本体设计 — 类型/Schema/版本/约束
├── construction/    # L2: 本体构建 — 摄入/抽取/流水线/分片
├── reasoning/       # L3: 本体推理 — 推断/意图/导航/解释/一致性
├── application/     # L4: 本体应用 — Chat/OMS/运行时/服务化/查询
├── registry/        # 跨层基础设施
├── health/          # 跨层监控
└── goal/            # 跨层目标管理
```

### 具体变更

| 层 | 变更 | 来源 |
|----|------|------|
| L1 `design/` | 收纳游离模块: `branch/`, `conflict/`, `computed/`, `inheritance/`, `view/`, `action/`, `cold_start/` | 顶层 → `design/` 下 |
| L2 `construction/` | **新建**。迁移: `design/ingestion/`, `design/services/{build,ingest,pipeline,qa_ontology}`, 顶层 `extraction/`, `sharding/` | 从 `design/` 和顶层迁移 |
| L3 `reasoning/` | **新建**。迁移: `assistant/rules/{type_inference,constraint}`, `cognition/{intent,navigation,explanation,thought_graph}`, `health/` 校验 | 从 4 个模块汇聚 |
| L4 `application/` | 执行 ADR-050: 合并三套 AI 助手为 `application/chat/`。保留 OMS/runtime/servitization/query_api/team_agent | `ontology/assistant/` + `core/assistant/` + `core/chat/` → `application/chat/` |

### 四层契约矩阵

```
                  L1 Design         L2 Construction    L3 Reasoning
L2 Construction  DesignContract           —                —
L3 Reasoning     DesignContract    BuildResultContract      —
L4 Application   DesignContract    BuildResultContract   ReasoningSvcContract
```

所有 Contract 返回 Frozen Dataclass Views，禁止直接引用内部实现类。

## Consequences

### 变得更容易
- 每个层次职责单一，新成员入职时"设计→构建→推理→应用"的认知模型与代码结构一一对应
- 构建流水线可独立演进（替换摄入策略、优化抽取算法），不影响设计层
- 推理服务有统一入口，AI 助手通过 `ReasoningServiceContract` 调用，可替换实现（如本地规则引擎 vs LLM-based 推理）
- AI 助手三合一后消除双 SSE 协议、双会话管理的维护负担

### 变得困难/需要注意事项
- 迁移工期约 4-6 周（Phase A 推理→B 构建→C 应用→D 文档），需分阶段执行确保不破坏现有功能
- 迁移期间需保持向后兼容（`__getattr__` 桥接），减少对下游调用方的冲击
- `cognition/` 模块推理代码迁移后需重新审视其定位（建议保留为「用户级认知引擎」而非「本体推理服务」）
- `harness/`（数据集成编排）需在迁移期间评估是否归入 L2 `construction/`
- `ingestion_split/` 与 `construction/ingestion/` 功能重叠，需在迁移时择一整合
- 需补充 3 个新 ADR：L2 构建契约、L3 推理契约、L4 内部契约

### 风险
- **中等风险**: 大规模文件迁移可能引入导入路径断裂，需要全面的集成测试覆盖
- **低风险**: Contract 抽象层增加间接性，但已有 `design/contract/` 验证可行

## 迁移路线图

| Phase | 内容 | 工期 | 优先级 |
|-------|------|------|--------|
| A | 建立 L3 `reasoning/`，定义 `ReasoningServiceContract`，汇聚推理代码 | 1-2 周 | ⭐ 最优先 |
| B | 拆分 L2 `construction/`，迁移构建+摄入+流水线 | 1 周 | 高 |
| C | 执行 ADR-050（三合一）+ 游离模块归属 | 1 周 | 高 |
| D | 文档化 + Contract 补充 + 架构图更新 | 持续 | 中 |
