# ADR-068: 本体模块四层分层架构（Design → Construction → +Reasoning → Application）

## Status
Accepted

## Context

当前本体模块 `odap/biz/core/ontology/` 名义上拆分为 `design/`（本体设计）和 `application/`（本体应用）两个子系统，实际存在以下结构性问题：

### 问题清单

1. **构建逻辑混在设计层**: `design/services/` 的 12 个服务中有 4 个属于构建阶段（`build_service`, `ingest_service`, `pipeline_service`, `qa_ontology_builder`），与版本管理、编辑锁等设计阶段服务平级混放。`ingestion_split/` 是独立的平行摄入系统，与 `design/ingestion/` 功能重叠。

2. **AI 推理能力散落**: 类型推断在 `assistant/rules/`，意图识别在 `cognition/impl/`，一致性校验在 `health/` —— 4 个模块分散管理，无统一入口，无契约约束。

3. **三套 AI 助手并存**: `ontology/assistant/`（T063, AG-UI）、`core/assistant/`（plugin, tool-call）、`core/chat/`（unified）三套协议不同、功能重叠。

4. **application/ 职责膨胀**: 7 个子模块覆盖元数据、运行时、服务化、数据集成、查询、智能体，缺乏内部契约。

5. **8 个游离模块**: `branch/`, `conflict/`, `computed/`, `inheritance/`, `view/`, `action/`, `cold_start/`, `extraction/` 无明确层级归属。

6. **cognition/ 模块定位模糊**: 用户认知引擎的推理代码（意图识别/知识导航/解释/思维图谱）与本体模块的推理功能存在概念重叠，当前分属两个独立模块。

### 业务驱动

本体领域存在天然的三阶段生命周期：**Design（设计 schema）→ Build（构建实例）→ Apply（应用交互）**。此外，AI 增强能力（类型推断、一致性校验）作为一个横向技术能力层贯穿三层。当前两层架构没有覆盖 Build 阶段，也缺乏对 AI 推理能力的统一管理。

### 多智能体论证过程

本决策经过三视角独立审查（2026-07-18）：

- **领域审查**: Design 和 Construction 通过 DDD 五项有界上下文测试（通用语言、领域专家、生命周期、不变量、变更耦合），确认应分离。AI 能力（类型推断/一致性）不构成独立的领域上下文，但作为共享技术能力层集中管理有架构价值。
- **代码审查**: 现有 120+ 跨模块 import 可通过 `__getattr__` 兼容层平滑迁移；24 个路由可保留在原地（薄壳模式）；15 个 SQLite 数据库路径不受影响；`ingestion_split/` 应作为主摄入系统保留。迁移工期 10-16 个工作日。
- **文档审查**: ADR-038/048/049 的「双引擎模型」与本文案的「分层模型」是递进替代关系；OADP（ADR-050）是正交的业务语义视角，不冲突；存在 3 组 ADR 编号冲突需同步修复。

## Decision

将本体模块重组为**3+1 分层架构**（3 个领域层 + 1 个技术能力层）：

```
odap/biz/core/ontology/
├── design/              # L1: 本体设计 (领域层)
│   ├── contract/        #   DesignContract (只读，Frozen Views)
│   ├── model/           #   类型定义: EntityType / Property / Relation
│   ├── schema/          #   Schema 文档定义
│   ├── version/         #   版本管理
│   ├── engine/          #   Schema 验证 + 审计引擎
│   ├── branch/          #   分支与合并 ← 从顶层迁移
│   ├── conflict/        #   冲突解决 ← 从顶层迁移
│   ├── computed/        #   计算属性 ← 从顶层迁移
│   ├── inheritance/     #   继承系统 ← 从顶层迁移
│   ├── view/            #   对象视图 ← 从顶层迁移
│   ├── action/          #   动作类型定义 ← 从顶层迁移
│   ├── cold_start/      #   冷启动模板 ← 从顶层迁移
│   └── services/        #   设计层服务 (仅保留: version/edit_lock/search/transform/schema_validation)
│
├── construction/        # L2: 本体构建 (领域层) ★ 新建
│   ├── contract/        #   BuildResultContract (只读，Frozen Views)
│   ├── ingestion/       #   数据摄入 (合并 ingestion/ + ingestion_split/)
│   │   ├── api/         #     原 ingestion/ 的 API 层
│   │   ├── impl/        #     原 ingestion/ 的 PDF/Word/OCR + ingestion_split/ 的新闻/爬虫/DB
│   │   ├── services/    #     统一 IngestionService
│   │   └── storage/     #     SQLite 存储
│   ├── extraction/      #   信息抽取 ← 从顶层迁移
│   ├── pipeline/        #   构建流水线 (从 design/services/ 迁移)
│   │   └── services/    #     build_service / ingest_service / pipeline_service / qa_ontology_builder
│   ├── quality/         #   构建质量验证 (实例级) ★ 新建
│   └── sharding/        #   分片策略 ← 从顶层迁移
│
├── reasoning/           # +AI: 推理能力层 (技术层) ★ 新建
│   │                   #    注意: reasoning/ 是技术能力层而非领域层。
│   │                   #    它聚合服务于 L1/L2/L3 的 AI 增强能力，
│   │                   #    通过 ReasoningServiceContract 统一暴露。
│   ├── contract/        #   ReasoningServiceContract
│   ├── inference/       #   类型推断 + 约束建议 (从 assistant/rules/ 迁移)
│   ├── consistency/     #   跨层一致性校验 (从 health/ + design/services/validation 迁移)
│   └── services/        #   UnifiedReasoningService 统一入口
│
├── application/         # L3: 本体应用 (领域层)
│   ├── chat/            #   统一 AI 助手 (三合一: ontology/assistant + core/assistant + core/chat)
│   │   ├── engine/      #     UnifiedChatService
│   │   ├── tools/       #     本体编辑工具 (design_tools / write_tools)
│   │   ├── retrieval/   #     RAG 检索引擎 (vector/BM25/graph)
│   │   └── renderers/   #     渲染器 (chart/temporal/report/thinking)
│   ├── intent/          #   意图识别 ← 从 cognition/ 迁移
│   ├── navigation/      #   知识导航 ← 从 cognition/ 迁移
│   ├── explanation/     #   解释引擎 ← 从 cognition/ 迁移
│   ├── thought_graph/   #   思维图谱 ← 从 cognition/ 迁移
│   ├── oms/             #   对象元数据服务 (只读缓存)
│   ├── runtime/         #   运行时引擎 (World State / 状态机)
│   ├── servitization/   #   API 服务化部署
│   ├── query_api/       #   NL 查询 API
│   └── team_agent/      #   团队智能体协同
│
├── registry/            # 跨层: TypeRegistry 统一类型入口
├── health/              # 跨层: 健康检查与质量监控
└── goal/                # 跨层: 目标管理
```

### 具体变更汇总

| 操作 | 内容 | 影响范围 |
|------|------|---------|
| **新建** | `construction/` 目录 + BuildResultContract | 从 design/services/ 迁移 4 个服务 |
| **新建** | `reasoning/` 目录 + ReasoningServiceContract | 从 4 个模块汇聚 AI 推理代码 |
| **合并** | ingestion/ + ingestion_split/ → construction/ingestion/ | ingestion_split 作为主系统保留 |
| **迁移** | 8 个游离模块归属 L1 design/ | branch, conflict, computed, inheritance, view, action, cold_start, extraction |
| **合并** | ontology/assistant/ + core/assistant/ + core/chat/ → application/chat/ | 三套 AI 助手统一入口 |
| **迁移** | cognition/ 的推理代码 → application/ | intent, navigation, explanation, thought_graph |
| **删除** | cognition/ 模块 | 推理能力不再独立于本体模块外 |
| **淘汰** | ADR-038/048/049 标记 Superseded | 双引擎模型被本方案替代 |

### 3+1 契约矩阵

```
                  L1 Design         L2 Construction    +AI Reasoning
L2 Construction  DesignContract           —                 —
+AI Reasoning    DesignContract    BuildResultContract       —
L3 Application   DesignContract    BuildResultContract   ReasoningSvcContract
```

所有 Contract 返回 Frozen Dataclass Views，禁止直接引用内部实现类。

### reasoning/ 层定位声明

`reasoning/` 被明确定义为**技术能力层**（Technical Capability Layer）而非**领域层**（Domain Layer）。它与 L1/L2/L3 的关系是横向注入而非纵向依赖：

- 它聚合了当前散落各处的 AI 增强功能（类型推断、约束建议、一致性校验）
- 它不引入新的领域概念——不定义 Entity/Relation/Property，只操作已有的领域对象
- 它通过 `ReasoningServiceContract` 提供统一推理入口，可替换实现（规则引擎 / LLM-based / 混合）
- 未来如果某能力成熟到可以独立演化为领域概念，可以从技术层升级为领域层

## Consequences

### 变得更容易
- Design 和 Construction 独立演进：Schema 变更不影响流水线，数据源变更不影响版本管理
- AI 推理能力有统一入口和契约，AI 助手通过 `ReasoningServiceContract` 调用
- 三套 AI 助手合并后消除双 SSE 协议、双会话管理、双 Hook 的维护负担
- 新成员入职时"设计 schema → 构建实例 → AI 辅助推理 → 应用交互"的认知模型与代码结构对应

### 变得困难/需注意
- 迁移工期 10-16 个工作日（4 阶段：预备→核心层→服务层→清理），需分阶段防止破坏
- 迁移期间需通过 `__getattr__` 桥接保持向后兼容（120+ 外部 import）
- 24 个路由采用"薄壳原地保留"策略，避免 API 前缀变更
- `ingestion/` 和 `ingestion_split/` 合并时需以 ingestion_split 为主系统
- `harness/`（数据集成编排）评估是否归入 L2 construction/ 或保留在 application/
- 需补充 2 个新 ADR：BuildResultContract 设计、ReasoningServiceContract 设计

### 风险与缓解
| 风险 | 等级 | 缓解 |
|------|------|------|
| 大规模 import 路径断裂 | 高 | `__getattr__` 兼容层 + 分阶段弃用 + CI lint 阻断 |
| ingestion 双系统合并 | 高 | 以 ingestion_split 为主，逐步替换 ingestion 调用 |
| reasoning/ 层概念混淆 | 中 | 明确标注为技术层，README 中强调非领域层 |
| 迁移期间系统不可用 | 低 | 灰度发布：先部署兼容层，再逐模块迁移 |
