# ADR-076: 决策智能架构 — 决策作为一等公民对象

## Status

**Accepted（已批准）** (2026-08-15 评审；2026-08-16 修订轮；2026-08-16 批准开工 Phase 1)

> 本文档已经过 9 轮 grilling 审查（决议记录见 §11），并对 Graphiti 协作面做了源码级验证（结论见 §10）。**2026-08-16 第 10-11 轮修订**：API 面 5→7 端点（新增因果边建立 `add_causal_relationship` 与落库前规则门禁 `check_decision_rules`）、因果边类型化（`CAUSED_BY`/`INFLUENCED_BY`/`PRECEDENT_FOR`），对齐 Semantica Decision Intelligence 全 API 面。实施前必须完成 §12 Checklist 的前置项。

## Context

ODAP 定位为"本体驱动的分析决策平台"，但其决策能力与该定位之间存在**最大缺口**。

### 现状诊断

当前 `biz/decision/` 模块包含三个子模块：

| 子模块 | 职责 | 现状 |
|---|---|---|
| `decision_pipeline/` | OADP 五阶段流水线（analyze→decide→validate→perform→feedback） | 产出 `DecisionResult`（含 `decision_id`、`recommended_option`、`reasoning`），但**仅作为流水线内存对象**，未持久化 |
| `decision_recommendation/` | 基于 `RecommendationRequest` 产出 `DecisionRecommendation` | 包含 `supporting_evidence`、`rationale` 字段，但**无后续追溯能力** |
| `action_service/` | 执行动作 + 反馈闭环 | `feedback_loop.close_loop()` 仅返回 `{action_id, graph_updated, episode_created, hook_emitted}` 四标志，**实质反馈内容未返回，且与原决策无外键关联** |

经代码探查确认的**三大缺陷**：

1. **决策非一等公民**：`DecisionResult.decision_id` 在 `_decide()` 中生成（`dec_{uuid}`），仅作为 `PipelineResult` 的内存字段返回，**无持久化存储**。流水线执行结束后，决策及其上下文、理由、备选项全部丢失。

2. **无因果链追溯**：`DecisionResult.reasoning` 仅是一段文本，无结构化的证据链。且 `_analyze()` 产出的是实体（`retrieval.objects` 的 `object_id`），**全链路从未接触过 Episode ID**。

3. **无先例检索与影响分析**：
   - 无法回答"过去类似情境下做过什么决策？结果如何？"
   - 无法回答"这个决策执行后，影响了哪些后续事实/决策？"
   - `ActionRequest` 无 `decision_id` 字段，执行记录无法反查所属决策，反馈闭环断裂

另探查发现**既存隔离漏洞**：`AnalysisInput.workspace_id` 为 `Optional[str]` 且由客户端透传，`_analyze()` 调用检索时未传 workspace 参数——现状下决策可能在跨工作空间数据上进行（本 ADR §7 顺带修复）。

### 根因

ODAP 的决策模块设计为**过程编排**（pipeline 流转），而非**决策资产**（持久化、可追溯、可复用的一等公民对象）。这与 Semantica 的决策智能能力存在本质差距——Semantica 的 `record_decision()` / `trace_decision_chain()` / `find_similar_decisions()` / `analyze_decision_impact()` 四大 API 将决策视为可审计、可检索、可分析的图节点。

### 触发场景

- **可审计 100%**：ADR-074 要求"过程可重现"，但决策推理过程无法重现
- **辅助决策**："上次类似情况下我们怎么决策的？"——无法回答
- **决策复盘**：执行结果与预期偏差时，需回溯决策上下文和理由——无法关联
- **OADP 闭环**：ADR-050/051 要求"执行结果回传→更新决策认知"，当前闭环断裂

### 关联 ADR

- **ADR-074**（分层审计）：决策记录复用其 Graphiti 事实演化审计通道（`save_audit_episode`）；影响分析的强能力依赖其 edge invalidation 落地
- **ADR-051**（闭环反馈机制）：决策记录承接反馈，形成完整闭环
- **ADR-002**（Graphiti 双时态）：决策记录带 `valid_time` + `transaction_time`
- **ADR-050**（OADP 业务语义）：决策是 "Decide" 阶段核心产物
- **ADR-023/041**（工作空间隔离）：决策记录强制隔离

## Decision

### 1. 核心定位：决策作为一等公民对象

| 维度 | 现状（ADR-076 前） | 调整后（ADR-076 后） |
|---|---|---|
| 持久化 | ❌ 内存对象 | ✅ 单一节点表示（Graphiti EntityNode 本体 + Cypher 扩展字段） |
| 标识 | `decision_id` 仅在 `PipelineResult` 中 | ✅ 由持久化服务统一生成，全链路穿透 |
| 因果链 | ❌ `reasoning` 为文本 | ✅ 双层证据链：`BASED_ON`→实体 + `DERIVED_FROM`→Episode |
| 先例检索 | ❌ 无 | ✅ Graphiti `search_()` 向量检索 + `group_ids` 索引级隔离 |
| 影响分析 | ❌ 无 | ✅ 弱影响分析（Phase 1）/ 强影响分析（依赖 ADR-074） |
| 反馈闭环 | ⚠️ 脱节 | ✅ `TRIGGERED` 边 + outcome 回填（失败也回填） |
| 空间隔离 | ⚠️ 有漏洞（客户端透传、可空） | ✅ 路由层覆盖 + 非空拒绝 + 双轨过滤 |

### 3. DecisionRecord 数据模型

```python
from datetime import datetime, timezone
from typing import Optional, List, Dict, Any
from pydantic import BaseModel, Field
import uuid


class DecisionRecord(BaseModel):
    """决策记录一等公民对象"""

    decision_id: str = Field(
        default_factory=lambda: f"dec_{uuid.uuid4().hex[:12]}",
        description="决策唯一标识（由持久化服务生成，全链路唯一权威）"
    )
    node_uuid: Optional[str] = Field(
        None, description="Graphiti EntityNode uuid（写入后回填，Cypher 扩展字段的挂载点）"
    )

    # 决策上下文（工作空间隔离边界，必填）
    workspace_id: str = Field(description="工作空间ID（非空，服务层强制校验）")
    scenario_id: Optional[str] = Field(None, description="场景ID")
    agent_id: Optional[str] = Field(None, description="决策AgentID")

    # 决策输入
    query: str = Field(description="触发决策的原始查询")
    context: Dict[str, Any] = Field(
        default_factory=dict, description="决策上下文（分析摘要、约束条件等）"
    )

    # 双层证据链（grilling Q4 决议）
    evidence_entity_ids: List[str] = Field(
        default_factory=list,
        description="主证据：analyze 阶段实体的 object_id 列表（BASED_ON 边，必有值）"
    )
    evidence_episode_ids: List[str] = Field(
        default_factory=list,
        description="辅证据：经 Graphiti MENTIONS 关系反查的来源 Episode ID（DERIVED_FROM 边，可空）"
    )

    # 决策推理
    reasoning: str = Field(description="决策理由（自然语言）")
    reasoning_trace: List[Dict[str, Any]] = Field(
        default_factory=list,
        description="推理路径结构化记录（为 ADR-075 推理引擎 rule_trace 预留落地点）"
    )

    # 决策选项（序列化的 DecisionOption）
    recommended_option: Optional[Dict[str, Any]] = None
    alternative_options: List[Dict[str, Any]] = Field(default_factory=list)

    # 决策结果（执行后回填；OPA 拒绝/执行失败也必须回填）
    outcome: Optional[str] = Field(
        None, description="success / failure / partial / rejected"
    )
    outcome_details: Optional[Dict[str, Any]] = Field(
        None, description="执行记录摘要 + feedback_pipeline 四标志"
    )
    outcome_recorded_at: Optional[datetime] = None

    # 策略校验
    opa_approved: bool = False
    opa_decision: Optional[Dict[str, Any]] = None

    # 置信度
    confidence: float = Field(0.0, ge=0, le=1)

    # 双时态（复用 ADR-002）
    valid_time: datetime = Field(description="决策生效时间（业务时间）")
    transaction_time: datetime = Field(
        default_factory=lambda: datetime.now(timezone.utc)
    )

    # 因果关系
    parent_decision_id: Optional[str] = Field(
        None, description="父决策ID（CAUSED_BY 边）"
    )
```

### 4. 核心 API（7 端点，对齐 Semantica Decision Intelligence 全 API 面）

#### 4.1 `record_decision()` — 决策持久化

```
POST /api/decisions
```

**单一表示原则（grilling Graphiti 验证问题 2 修正）**：Decision 节点**本体即一个 Graphiti EntityNode**，禁止"Cypher 建一个节点 + Graphiti 再建一个节点"的双重表示。写入路径：

1. 构造 `EntityNode`（`name=decision_id`、`labels=['Decision']`、`group_id=workspace_id`、`summary=query + reasoning` 摘要），经 **EntityNode 三步法**写入：`await node.generate_name_embedding(embedder)` → `await node.save(driver)`（embedding 进向量索引）。**0.29.2 已核验不存在 `graphiti.nodes` 命名空间**（见 §12 前置项 #1）
2. 拿到 `node_uuid` 后，用 Cypher `SET` 将扩展字段（context/options/outcome/trace 等 JSON）挂到**同一 uuid** 节点上
3. 建边：`BASED_ON`→evidence 实体；`DERIVED_FROM`→evidence Episode（经 MENTIONS 反查，可为空）；`CAUSED_BY`→父决策（如有）
4. 审计副本：调用 **`GraphManager.save_audit_episode()`**（复用既有唯一 EpisodicNode 实例化点，`event_type="decision_record"`，零 LLM）；失败不阻断主流程，后台任务可扫描补写

`decision_id` 由此服务生成并回填给调用方，pipeline 内存对象中的 ID 永远等于持久化 ID。

#### 4.2 `trace_decision_chain()` — 因果链追溯

```
GET /api/decisions/{decision_id}/chain?max_depth=5
```

Cypher 变长路径遍历 `BASED_ON | DERIVED_FROM | CAUSED_BY`（起点强制 `workspace_id` 过滤），返回双层证据：

- **实体层**（必有值）：决策直接依据的事实实体
- **Episode 层**（可空）：事实的原始出处（数据源、采集时间）
- **父决策链** + 结构化 `reasoning_trace`

> ⚠️ Episode 层覆盖率取决于实体是否经由 `add_episode` 管线产生（MENTIONS 边仅由该管线创建；经 Cypher 直写的实体无 MENTIONS 边）。覆盖率随 ADR-074 修正推进逐步提升，详见 §10 问题 3。

#### 4.3 `find_similar_decisions()` — 先例搜索

```
GET /api/decisions/similar?query=...&top_k=10&time_from=...&time_to=...
```

**grilling Q1 修正 + Graphiti 验证问题 1 修正**：

- **用 `search_()` 而非 `search()`**：`search()` 返回 `list[EntityEdge]`（边列表），不含节点；`search_()` 返回 `SearchResults{edges, nodes, episodes, communities}`，取 `.nodes`
- 调用形态：`graph.search_(query, group_ids=[workspace_id], search_filter=SearchFilters(node_labels=['Decision'], ...))`，`group_ids` 与 label 过滤均**下推到图库查询层**（索引级隔离，无召回精度损耗）
- 可选时间过滤走 `SearchFilters` 的 temporal 约束（双时态）
- 返回含 `outcome` 的先例列表，支持"过去类似情况结果如何"

> ✅ 已核验（2026-08-15，前置项 #1 完成）：0.29.2 中 `search_()` 签名含 `group_ids` + `search_filter` 参数；`SearchFilters` 含 `node_labels`/`edge_types`/`valid_at`/`invalid_at`/`property_filters`，label 过滤可用，**无需降级**。`EntityEdge` 含 `valid_at`/`invalid_at`/`expired_at`（§4.4 强影响分析的字段基础确认存在）；Episodic→Entity 边类为 `EpisodicEdge`（MENTIONS 语义）。

#### 4.4 `analyze_decision_impact()` — 下游影响分析（分档实现，grilling Q5 决议）

```
GET /api/decisions/{decision_id}/impact
```

**Phase 1 交付"弱影响分析"**（不依赖 edge invalidation，三类确定性影响）：

1. **衍生决策**：`(:Decision)<-[:CAUSED_BY]-(:Decision)` 反向遍历
2. **目标实体后续变更**：`TRIGGERED`→ActionRecord + 目标实体 `valid_time`/`updated_at` 时序比较
3. **同证据共现决策**：共享 `BASED_ON` 证据实体的后续决策

**强影响分析**（invalidation 边遍历、失效事实清单）**显式声明依赖 ADR-074 落地**；在此之前返回空集合，且 API 响应带 `impact_completeness: "partial" | "full"` 字段显式标注数据完整度，前端据此提示。

#### 4.5 `add_causal_relationship()` — 因果边建立（2026-08-16 修订新增）

```
POST /api/decisions/{decision_id}/causal-links
```

显式建立决策间因果边，边类型三选（对齐 Semantica `CAUSED`/`INFLUENCED`/`PRECEDENT_FOR` 分类）：

| 边类型 | 语义 | 建立方式 |
|---|---|---|
| `CAUSED_BY` | 直接导致（原 `parent_decision_id` 语义） | record 时自动（有父决策）或本端点显式 |
| `INFLUENCED_BY` | 弱影响（上下文参考但未直接采纳） | 本端点显式 |
| `PRECEDENT_FOR` | 先例引用留痕（旧决策 → 新决策方向） | `find_similar_decisions` 结果被实际采纳时**自动建立**——"先例被引用"这件事本身留痕 |

约束：两端决策必须同 workspace；`CAUSED_BY` 链上做环检测，禁止成环。

#### 4.6 `check_decision_rules()` — 落库前规则门禁（2026-08-16 修订新增）

```
POST /api/decisions/check-rules
```

决策产出后、record 落库前的前置合规门禁（对齐 Semantica 前置哲学——比事后审计更强）：

- **Phase 1**：门禁 = 现有 OPA 权限校验前移（复用 `opa_approved`/`opa_decision` 字段承载结果，语义从"action 执行前"前移到"record 落库前"）
- **前向依赖声明**：ADR-075 落地后，业务规则（BusinessRule）加入第二道门禁——权限门禁管"能不能做"，业务规则门禁管"合不合理"
- 门禁拒绝的决策可选择以 `outcome=rejected` 落库留痕（推荐）或丢弃

#### 4.7 `update_decision_outcome()` — 结果回填（内部调用）

```
PATCH /api/decisions/{decision_id}/outcome
```

数据来源为 `action_record` 本体（status/执行结果/时间戳），`close_loop` 返回的四标志存入 `outcome_details.feedback_pipeline`。**OPA 拒绝（`rejected`）与执行失败（`failure`）也必须回填**，否则决策永远"无结果"，先例检索与影响分析失真。

### 5. 存储设计

#### 5.1 图模型（单一表示）

```
节点（一个决策 = 一个节点，Graphiti EntityNode 本体）：
  (:Entity:Decision {
    uuid,                        # Graphiti 管理，扩展字段挂载点
    name: decision_id,
    group_id: workspace_id,      # Graphiti 原生多租户分区（索引级隔离）
    labels: ['Decision'],
    summary: query + reasoning,  # name_embedding 向量化来源
    name_embedding,              # Graphiti embedder 生成
    # —— 以下为 Cypher SET 扩展字段 ——
    context, reasoning_trace, recommended_option, alternative_options,
    outcome, outcome_details, outcome_recorded_at,
    opa_approved, opa_decision, confidence,
    scenario_id, agent_id, parent_decision_id,
    valid_time, transaction_time,
    workspace_id                 # 属性冗余（Cypher 过滤轨）
  })

边类型：
  (:Decision)-[:BASED_ON]->(:Entity)              # 主证据（必有值）
  (:Decision)-[:DERIVED_FROM]->(:Episodic)        # 辅证据（经 MENTIONS 反查，可空）
  (:Decision)-[:CAUSED_BY]->(:Decision)           # 决策因果链（直接导致）
  (:Decision)-[:INFLUENCED_BY]->(:Decision)       # 决策弱影响（2026-08-16 修订新增）
  (:Decision)-[:PRECEDENT_FOR]->(:Decision)       # 先例引用留痕（2026-08-16 修订新增，旧决策→新决策）
  (:Decision)-[:TRIGGERED]->(:ActionRecord)       # 决策→执行关联（Q3 决议）
  (:Decision)-[:TARGETS]->(:Entity)               # 决策目标实体

索引与约束（应用启动幂等创建，CREATE ... IF NOT EXISTS）：
  uuid 约束（Graphiti build_indices_and_constraints 已含）
  CREATE INDEX FOR (d:Decision) ON (d.workspace_id, d.valid_time)
```

#### 5.2 驱动选型（grilling Q7 决议）

`Neo4jDecisionStore` 自建 **`AsyncGraphDatabase.driver()` 模块级单例**，所有 Cypher 走 `async with driver.session()`：

- **不复用** `GraphManager.neo4j_driver`（同步驱动，在 async 上下文会阻塞事件循环）
- 连接参数走现有配置模块读 `NEO4J_URI`（Podman 容器网络内为 `graphiti-neo4j:7687`），禁止硬编码
- prod 模式 uvicorn 4 workers = 4 个驱动实例，Neo4j 连接数计入容量评估
- `graph_service.py` 中同步 driver 的既有用法为**历史技术债**，本 ADR 不扩散、不在 Phase 1 偿还

#### 5.3 向量检索与空间隔离（grilling Q8 决议）

- `group_id = workspace_id`：Graphiti 原生分区，所有检索函数（全文/向量/BFS）将其下推到查询层——**索引级隔离**
- **现状已对齐**：`graph_service.py:1165` 的 `save_audit_episode` 已使用 `group_id=workspace_id`，语义无冲突；实施前小探查确认无其他占用即可，如冲突改用 `ws_{workspace_id}` 命名
- **双轨过滤**：Graphiti 侧 `group_ids` 管向量检索；Cypher 侧 `workspace_id` 属性管图遍历——各自强制
- **零新增依赖**：embedding 复用 Graphiti 内置 embedder（`Graphiti(uri..., embedder=embedder)`，`graph_service.py:662-668` 已配置），**不新增 embedding 服务，`pyproject.toml` 零变更、镜像零重建**

### 6. 与现有模块的集成（grilling Q3 决议：decision_id 全链路穿透）

#### 6.1 decision_pipeline

```python
async def _decide(self, analysis, input_data) -> DecisionResult:
    # 前置校验：workspace_id 非空（顺带修复既存隔离漏洞）
    if not input_data.workspace_id:
        raise ValueError("workspace_id is required for decision recording")

    # ... 现有推荐逻辑产出 decision（不再自行生成 decision_id）...

    # ★前置规则门禁（2026-08-16 修订：落库前先过门禁，见 §4.6）
    from odap.biz.decision.decision_record import get_decision_service
    gate = await get_decision_service().check_decision_rules(
        workspace_id=input_data.workspace_id, decision=decision,
    )
    decision.opa_approved = gate.approved
    decision.opa_decision = gate.details

    # ★持久化（失败不阻断主流程，warning log）
    try:
        record = await get_decision_service().record_decision(
            DecisionRecord(
                workspace_id=input_data.workspace_id,  # 路由层已覆盖为服务端值
                query=input_data.query,
                evidence_entity_ids=[e['object_id'] for e in analysis.entities[:10]],
                reasoning=decision.reasoning,
                recommended_option=...,
                valid_time=datetime.now(timezone.utc),
                ...
            )
        )
        decision.decision_id = record.decision_id  # 回填持久化 ID（唯一权威）
    except Exception as e:
        logger.warning(f"record_decision failed (non-blocking): {e}")
    return decision
```

#### 6.2 action_service 穿透

- `ActionRequest` 新增可选字段 `decision_id`，`_perform()` 传入
- `action_record` 落库携带该字段；Neo4j 建 `(:Decision)-[:TRIGGERED]->(:ActionRecord)` 边

### 7. 工作空间隔离（grilling Q6 决议：三件套）

1. **路由层覆盖**：按"JWT `ws_id` 声明 → 请求头 `X-Workspace-ID`（经 OPA/RBAC 校验访问权）"优先级解析，**覆盖**客户端 body 值。**前置项 #3 已核验（2026-08-15）**：JWT payload 原生含 `ws_id`/`ws_role` 声明（`jwt_service.issue_access_token` 签发，refresh 续签保持，`JWTPayload` 模型已解析），**声明存在且语义正确，无需改造 JWT 结构**；但路由层现状 `get_current_user` 仅返回 raw dict、无 workspace 解析封装，需新增 `get_current_workspace` 依赖（封装 `payload.get("ws_id")` + 非空校验 + 访问权校验）。`X-Workspace-ID` 机制**现状不存在**（无该头解析、无 workspace 切换接口，token 生命周期内 `ws_id` 固定）——Phase 1 切换空间走重新登录，`X-Workspace-ID` 覆盖记为可选增强项
2. **非空拒绝**：`decision_record` 服务入口校验 `workspace_id`，为空抛 422；pipeline `_decide()` 前置校验快速失败（顺带修复 `_analyze()` 不传 workspace 的既存漏洞）
3. **存储层双保险**：Cypher 读路径全部 `WHERE d.workspace_id = $workspace_id`；向量检索 `group_ids=[workspace_id]`

**隔离 Checklist**（评审强制确认）：

- [ ] `record_decision`：`workspace_id` 非空校验；EntityNode `group_id` = workspace_id
- [ ] `trace_decision_chain`：起点过滤含 workspace_id
- [ ] `find_similar_decisions`：`group_ids` 索引级过滤
- [ ] `analyze_decision_impact`：图遍历起点过滤
- [ ] `update_decision_outcome`：更新条件含 `decision_id AND workspace_id`
- [ ] `add_causal_relationship`：两端决策同 workspace 校验 + `CAUSED_BY` 环检测
- [ ] `check_decision_rules`：门禁输入的 `workspace_id` 来自路由层解析（非客户端透传）

### 10. Graphiti 协作面验证结论（2026-08-15 源码级核查）

**验证方式**：本机未安装 graphiti-core 源码（uv.lock 锁定 0.29.2，宿主机 `.venv` 仅开发工具——Podman 部署下属正常）；库 API 经官方文档/DeepWiki 源码索引验证，项目现状经代码探查验证。

**验证为合理的决策**：

| 决策 | 验证结论 |
|------|----------|
| `group_id = workspace_id` | Graphiti 原生多租户分区，全部检索函数下推到查询层；ODAP 现状已对齐（`save_audit_episode`） |
| EpisodicNode 零 LLM 审计 | 异步方法，项目已有唯一实例化先例 |
| 自建异步驱动 | Graphiti driver 本身异步；避开 `GraphManager._run_async()`（每次调用新建事件循环）的既有隐患 |
| embedding 复用 | Graphiti 初始化已配置 embedder，能力客观存在（藏在 Graphiti 内部而非 `infra/llm/`） |

**修正的问题**：

| # | 问题 | 修正 |
|---|------|------|
| 1 | `search()` 返回 `EntityEdge` 列表不含节点，原决议无法过滤 Decision 节点 | 改用 `search_()`（`SearchResults.nodes`）+ `SearchFilters` label 过滤 |
| 2 | "Cypher 建 Decision 节点 + 注册进 Graphiti 索引"会产生**双重表示**（两个节点、uuid 不一致、边挂错） | 单一表示：节点本体即 Graphiti EntityNode，扩展字段 Cypher `SET` 挂同一 uuid |
| 3 | MENTIONS 边仅由 `add_episode` 管线创建，Cypher 直写实体无 MENTIONS；且现存 6 处 `add_episode` 均未传 group_id | `DERIVED_FROM` 可空兜底（实体层必有值）；覆盖率局限显式写入文档 |

## Consequences

### 正面影响

- **决策可审计 100%**：全链路持久化，支撑 ADR-074 过程审计
- **辅助决策能力补齐**：先例检索 + 影响分析 + 因果链追溯
- **OADP 闭环完整**：Decide 与 Perform/Feedback 经 `decision_id` + `TRIGGERED` 边强关联
- **顺带修复既存漏洞**：pipeline 跨空间检索问题在集成时一并修复
- **零新增基础设施依赖**：embedding/向量索引/多租户分区全部复用 Graphiti 内置能力，镜像零重建
- **为 ADR-075 预留落地点**：`reasoning_trace` 字段承接确定性推理引擎的 rule_trace

### 负面影响与缓解

- **Neo4j 写入增加**：每决策 1 节点 + N 边 + 1 Episode——决策频率远低于查询，Episode 零 LLM，可控
- **pipeline 复杂度增加**：持久化与回填均为 try/except 非阻断调用，主流程不受可用性影响
- **prod 4 workers = 4 异步驱动实例**：连接数计入容量评估，官方驱动连接池管理
- **Episode 层证据覆盖不全**：MENTIONS 局限已显式文档化，实体层永远有值兜底

## Considered Options

1. **决策存 SQLite**——否决：因果链需图遍历，SQLite 无法高效支持
2. **复用 `add_episode` 存决策**——否决：每次 3-9 次 LLM 调用（ADR-074 明确禁止）
3. **新增独立 embedding 服务 + 向量库**——否决：Graphiti 内置 embedder + `group_id` 分区已覆盖需求，零新增依赖是重大部署优势
4. **Cypher 全量扫描做先例检索**——否决：决策增长后不可行；保留为 `search_()` 不可用时的临时降级
5. **影响分析阻塞等待 ADR-074**——否决：决策智能是 P0，串联等待延期数周；弱影响分析已覆盖 80% 复盘诉求
6. **决策节点 Cypher 直写 + 单独注册索引（双重表示）**——否决：双节点 uuid 不一致导致边挂错、索引与主存储分裂；改单一表示
7. **用 `search()` + 事后 label 过滤**——否决：返回 EntityEdge 列表无节点；且事后过滤损耗召回精度
8. **Phase 1 纯后端无前端**——否决：决策智能是面向用户的能力，缺前端载体无法收集真实反馈、评审缺验收物
9. **复用同步 driver + run_in_executor**——否决：线程切换开销 + 坏味道扩散；async driver 与 Graphiti 风格一致

## Reversibility

**中等**。

- **可逆**：`decision_record/` 子模块可独立移除；pipeline/action_service 集成点为可选调用，失败不阻断
- **不可逆**：已写入的 Decision 节点及其边建议保留为只读归档，不做级联删除

**回退方案**：移除子模块与集成调用，历史数据保留。
