# ADR-065: 微服务拆分演进预案与触发条件

## 状态
Accepted

## 上下文

ADR-046 已明确**模块化单体**为 Phase 4 基线，并规定了微服务拆分的三个触发条件（团队 8+、某模块需独立扩缩、有专职 SRE）。但 ADR-046 只说了"何时拆"，未定义"怎么拆"——一旦触发，团队缺乏可执行的抽取 playbook，容易在紧急情况下做出不可逆的草率拆分。

本 ADR 作为 ADR-046 的**操作补篇**，把"拆分预案"固化下来，确保可逆、可控。

## 决策

1. **季度评审门禁**：每季度末按 ADR-046 三条件评审。三者**同时满足**才启动拆分；任一不满足则继续单体。
2. **抽取单元 = 模块边界**：最小拆分单位即现有 `biz/` 子模块（如 `event_simulator`、`action_service`、`agent`），不得拆到函数级。
3. **接口不变原则**：从 in-process 调用改为 HTTP/gRPC，**接口签名（`I*` 抽象）保持不变**，调用方零改动。
4. **数据归属优先**：被拆模块若持有独立数据（如推演引擎的模拟数仓 ADR-022），优先随模块一起迁出，避免跨服务分布式事务。
5. **舱壁先行**：拆分前先在单体内对目标模块加**熔断 + 舱壁（Bulkhead）**（依赖 ADR-064 追踪），验证故障隔离有效，再物理拆出。
6. **回退预案**：拆出后保留"合回单体"的接口兼容层至少两个版本，确保可逆。

### 候选拆分优先级（仅当触发时）

| 模块 | 拆分动因 | 优先级 |
|------|----------|--------|
| `event_simulator` / `simulator` | CPU 密集推演，易成扩缩瓶颈 | 高 |
| `action_service` | 执行链路独立，写回频繁 | 中 |
| `agent` 编排 | 长任务、需独立扩容 Agent 池 | 中 |

## 后果

### 变得更容易
- 触发拆分时有章可循，避免应急草率决策。
- 接口不变 + 回退层，拆分可逆、风险可控。
- 舱壁先行，物理拆分前已验证隔离。

### 变得更难
- 需维护"接口兼容层"与回退路径（短期负担）。
- 拆分后引入网络序列化、服务发现、跨服务追踪（更依赖 ADR-064）。

## 可逆性
**高（设计目标）**。单体 → 微服务本就比反向容易；本 ADR 通过接口不变 + 兼容层把可逆性写进流程。

## 关联
- ADR-046（模块化单体基线 + 触发条件，本文为其补篇）
- ADR-064（可观测性是拆分前提）
- ADR-022（模拟数仓，候选拆分模块的数据归属）
- ADR-002 / ADR-003（图谱/OPA 保持独立部署，不参与应用层拆分）
