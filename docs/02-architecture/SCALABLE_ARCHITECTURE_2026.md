# ODAP 可扩展系统架构设计（2026–2027）

> **版本**: 1.0 | **日期**: 2026-07-08 | **作者**: 软件架构师
> **定位**: 近期（6–12 个月）可扩展性演进方案，叠加在现有 ADR 之上，不推翻既有决策
> **关联基线**: ADR-046（模块化单体）、ADR-041（工作空间隔离）、ADR-014（Skill 热插拔）、ADR-029（工具注册表）、ADR-027（Hook 系统）、ADR-002（Graphiti）、ADR-003（OPA）

---

## 0. 设计原则（与既有 ADR 一致）

本方案遵循 ADR-046 / ADR-030 的核心哲学：**延迟复杂度（delay complexity）**。

| 原则 | 含义 | 在本方案中的体现 |
|------|------|------------------|
| **可逆优先** | 优先选"容易回头"的决策 | 所有拆分/分层均保留 in-process 接口，按模块拆出可回退 |
| **单进程基线** | 维持模块化单体（ADR-046） | 不以微服务为默认，只在触发条件满足时才拆 |
| **接口隔离** | 跨模块只走 `I*` 抽象 | Skill / 图谱 / 租户隔离全部接口化 |
| **YAGNI** | 不为臆想规模买单 | 图谱分片、多区域、Service Mesh 明确推迟到 Phase 5+ |
| **Trade-off 显式** | 每个决策都说出放弃了什么 | 下文每个方案均附"变得更难" |

**当前硬约束（来自 ADR-046）**：团队 3–5 人、无专职 SRE、无 K8s、单 FastAPI 进程、Docker Compose、Neo4j 社区版（单数据库）。

## 1. 可扩展性三维目标

| 扩展驱动 | 当前状态 | 差距（Gap） | 6–12 月目标 |
|----------|----------|-------------|-------------|
| **① 领域 Skill / 团队规模** | `odap/tools/` 单体目录 + 热插拔（ADR-014）+ 注册表（ADR-029） | 多团队向同一代码库贡献 Skill，部署耦合、无法独立版本化、边界靠人工审查 | Skill 可独立打包/版本/灰度，契约测试守住模块边界 |
| **② 知识图谱数据规模** | 社区版 Neo4j 单库 + 标签过滤（ADR-041），无读写分离、无分层 | 单实例写入吞吐/锁竞争、双时态推理成本、RAG 延迟、备份窗口 | 读写分离 + 向量 offload（近）+ 冷热分层（中），分片推迟 |
| **③ 多租户 / 交付部署** | 工作空间级隔离（ADR-041），**非** per-customer 独立部署 | 无租户模型、无独立交付/数据/策略隔离、无部署自动化 | 租户感知隔离 + 部署蓝图（GitOps）+ 租户开通自动化 |

> ⚠️ 关键区分：**工作空间（Workspace）≠ 租户（Tenant）**。Workspace 是单部署内的场景隔离；Tenant 是给不同客户/部门**独立部署并隔离数据与策略**。本方案把 ADR-041 的隔离器从 `workspace_id` 升级为 `tenant_id + workspace_id` 两级，部署形态从"一个平台"演进为"一个平台模板 + N 个租户实例"。

## 3. 三大驱动的具体策略

### 3.1 驱动①：领域 Skill / 团队规模 → 插件化打包 + 契约测试

**问题**：`odap/tools/` 是单体目录，所有 Skill 同仓同进程。当 56+ 领域 Skill、多团队并行时：
- 任一 Skill 导入错误 → 整个进程启动失败（部署耦合）
- Skill 无法独立发版/灰度
- 边界靠"代码审查强制接口约束"（ADR-046 已标记此为**高风险**）

**选项对比**：

| 方案 | 描述 | 优点 | 放弃的东西 |
|------|------|------|-----------|
| A. Skill 插件包（推荐） | 每个领域 Skill 集打成独立包（wheel / 带 `skill.yaml` 清单的目录），运行时经 entry-point 发现，中央注册表（ADR-029）聚合；契约 `ISkill` + 契约测试 | 维持单进程性能与事务一致性；可独立版本/灰度；可逆 | 需引入打包与发现机制（~中等复杂度） |
| B. Skill 微服务 | 每个 Skill 独立进程，gRPC/HTTP 调用 | 故障/部署完全隔离 | 引入网络序列化、失去 in-process 事务、违背 ADR-046 当前基线 |
| C. WASM/容器沙箱 | 每 Skill 沙箱隔离 | 最强安全隔离 | 极重，6–12 月内过度工程 |

**决策（ADR-061）**：采用 **A**。定义 `ISkill` 契约接口（`execute / validate / metadata`），Skill 以"领域包"为单位独立版本化；复用 ADR-014 热插拔实现热加载/卸载；引入契约测试（pytest 框架，验证每个插件满足 `ISkill` 与资源边界）。模块边界由"人工审查"升级为"CI 强制契约 + ArchUnit 风格依赖方向测试"。

**后果**：部署耦合 ↓、独立版本化 ↑；代价是打包/发布流水线复杂度上升（一次性投入）。

---

### 3.2 驱动②：知识图谱数据规模 → 读写分离 + 向量 offload（近）+ 冷热分层（中）

**问题**：社区版 Neo4j 单库承载全部写入、双时态推理、RAG 检索。规模上升后：写入锁竞争、时序查询昂贵、检索延迟、备份窗口拉长。

**选项对比**：

| 方案 | 描述 | 优点 | 放弃的东西 |
|------|------|------|-----------|
| A. CQRS 读写分离 + 向量 offload | 写主库；读副本/只读视图承载问答检索；Embedding 检索 offload 到专用向量库（Milvus/Qdrant）；加查询缓存 | 写不被读拖垮；RAG 延迟↓；不依赖企业版 | 读副本有复制延迟（需定义可接受的陈旧窗口） |
| B. 图谱分片（Fabric / 多集群） | 按域/租户分片到多 Neo4j 实例 + 路由层 | 水平写扩展最强 | 需企业版 + 专职 SRE；运维复杂度陡增 |
| C. 冷热分层 | 活跃实体留 Neo4j 热；历史时序快照进对象存储/列存（Parquet+DuckDB） | 热库体积可控、备份快 | 跨冷热查询需访问层抽象；历史回溯路径变复杂 |

**决策（ADR-062）**：**分阶段**。
- **近（Q1–Q2）**：CQRS 读副本 + 向量检索 offload（复用现有 SiliconFlow `bge-m3` Embedder，指向独立向量库）+ 查询缓存。
- **中（Q2–Q3）**：冷热分层 PoC——双时态历史快照下沉冷存，热库只保留活跃窗口。
- **推迟（Phase 5+）**：图谱分片（B），待触发条件（单实例成瓶颈 + 有 SRE）满足再上。

**后果**：写入吞吐与检索延迟改善；代价是引入复制延迟（必须显式定义 SLA 内的陈旧度）与额外的存储组件运维。

---

### 3.3 驱动③：多租户 / 交付部署 → 租户感知隔离 + 部署蓝图

**问题**：当前 ADR-041 是单部署内的 workspace 隔离，无法支撑"给多个客户独立部署、隔离数据与策略"。

**选项对比**：

| 方案 | 描述 | 优点 | 放弃的东西 |
|------|------|------|-----------|
| A. 每租户独立部署（专用） + 部署蓝图 | 每客户一套栈（Compose/K8s NS），由 GitOps 蓝图统一生成与开通；隔离天然最强 | 隔离最强、合规友好；复用 ADR-046 单进程 | 运维成本随租户数线性增长 |
| B. 单部署多租户（逻辑隔离） | 一个平台服务多租户，`tenant_id` 隔离 | 运维成本最低 | 需极强隔离保证，漏洞即跨租户泄露 |
| C. 控制面 + 数据面 | 统一控制面管理多租户数据面 | 最可扩展 | 极重，远超当前团队能力 |

**决策（ADR-063）**：**A 为默认，B 为演进目标**。
- 将 `WorkspaceIsolator` 升级为 `TenantIsolator`：`tenant_id + workspace_id` 两级，路由图谱库/标签、OPA Bundle 前缀（`/tenants/{t}/workspaces/{w}/policies/`）、配置命名空间。
- 引入**部署蓝图（Deployment Blueprint）**：参数化 Compose/K8s 模板 + GitOps，新租户开通 = 生成一份带 `tenant_id` 的配置并自动部署。
- 维持"每租户一个模块化单体"（ADR-046）。当租户数量与运维成本失衡时，再评估向 B（逻辑多租户）演进。

**后果**：交付可复制、隔离强；代价是每租户运维成本线性增长（用自动化对冲）。

## 4. 横切前提：可观测性基线（ADR-064）

三大驱动都依赖"看得清"。没有统一追踪，规模化后无法定位跨模块/Skill/图谱的慢调用与故障传播。

**决策**：引入 OpenTelemetry 统一追踪（`trace_id` 贯穿 Agent Loop → Skill → Graphiti → OPA），Prometheus 指标 + 结构化日志；`trace_id` 注入现有审计日志（ADR-008）。这是 6–12 月所有工作的**前置基础**，放在 Q1 最先做。

## 5. 6–12 个月演进路线图

> 阶段命名承接现有 Phase 4（高级特性），本方案聚焦"可扩展性硬化（Scalability Hardening）"。

| 季度 | 主题 | 关键交付 | 关联 ADR | 验收标准 |
|------|------|----------|----------|----------|
| **Q1 (M1–M3)** | 地基与边界 | 可观测性基线；`ISkill` 契约 + 契约测试；`TenantIsolator` 原型；图谱 CQRS 读副本 + 向量 offload 落地 | 064, 061, 063, 062 | OTel trace 贯通核心链路；CI 契约测试拦截边界破坏；读副本承担 ≥70% 查询 |
| **Q2 (M4–M6)** | 数据规模与租户交付 | 冷热分层 PoC；部署蓝图 + 租户开通自动化；内部 Skill 市场注册表；首轮规模化压测 | 062, 063, 061 | 冷存接管历史快照；新租户开通 < 30min（自动化）；图谱 1M 节点压测达标 |
| **Q3 (M7–M9)** | 韧性与多实例 | 模块级熔断/舱壁（Bulkhead）；读副本自动扩缩；多租户部署管理台 | 046 补充, 063 | 单 Skill 故障不拖垮进程；读负载自动扩缩 |
| **Q4 (M10–M12)** | 演进就绪 | 微服务拆分预案定稿（触发条件 + 抽取 playbook）；容量规划；文档与演练 | 065 | ADR-065 抽取 playbook 可复述；容量基线建立 |

**节奏控制**：每季度末做一次"是否触发 ADR-046 微服务条件"的评审（团队人数、独立扩缩需求、SRE 到位情况）。未触发则继续模块化单体。

## 7. 风险与可逆性总览

| 风险 | 概率 | 缓解 / 可逆性 |
|------|------|---------------|
| 引入插件打包后发布流水线变复杂 | 中 | 一次性投入；插件接口稳定后即收益；可逆（回退为目录式 Skill） |
| 读写副本复制延迟导致问答读到旧数据 | 中 | 显式定义陈旧度 SLA；写后强一致路径走主库 |
| 租户独立部署运维成本线性增长 | 高 | 部署蓝图 + 开通自动化对冲；必要时演进到逻辑多租户（B） |
| 边界契约测试被绕过 | 中 | CI 强制门禁 + 架构依赖方向测试（ArchUnit 风格） |
| 过早做图谱分片 | 低 | 明确推迟到 Phase 5+，避免 YAGNI |

**一句话总结**：在模块化单体（ADR-046）的底座上，用**插件化 Skill + 读写分离图谱 + 租户感知部署蓝图 + 统一可观测性**四根支柱撑起近一年的扩展需求，所有决策保持可逆，微服务拆分仅作为触发条件满足后的预案（ADR-065）。
