## 2. 防腐机制

### 2.1 三层防腐策略

| 策略 | 说明 | 机制 |
|------|------|------|
| **预防 (Prevent)** | 防止文档与实现不一致 | 文档基线 + 变更前置检查 |
| **检测 (Detect)** | 发现已有不一致 | 定期完整性检查清单 §8 |
| **纠偏 (Correct)** | 修复文档漂移 | 归档废弃文档 + 更新路径引用 |

### 2.2 变更前置检查（每次文档变更必须）

1. 需求变更 → 更新 `00-requirements/req-ok.md` → 同步更新 `02-architecture/ARCHITECTURE.md`
2. 架构决策 → 创建新 ADR → 更新 `ARCHITECTURE.md` 引用
3. 模块变更 → 更新对应 `03-modules/*/DESIGN.md` → 同步更新 `ARCHITECTURE_FULL_CHAIN_DEEP.md`
4. 废弃文档 → 移至 `11-archive/`，保留演进历史，**禁止直接删除**

### 2.3 路径变更影响链

```
需求 req-ok.md → 架构 ARCHITECTURE.md → 模块 03-modules/
                                     ├── ADR 07-adr/
                                     ├── UI 04-ui/
                                     ├── 安全 05-security/
                                     └── DFX 06-dfx/
                                              ↓
                                      08-tasks/ TASK_BREAKDOWN.md
                                              ↓
                                      09-checklists/ CHECKLIST_v2.md
```

### 2.4 保真年限

| 文档层 | 最大无审阅间隔 | 过期标记 |
|--------|:------------:|---------|
| 需求 | 6 个月 | 需求变更时优先处理 |
| 架构 | 3 个月 | 架构审查时优先处理 |
| 模块 | 2 个月 | 模块迭代时更新 |
| ADR | 半年 | 被替代时标记为弃用 |

## 3. 文档生命周期管理

### 3.1 状态流转

```
草稿 → 评审中 → 正式 → 维护中 → 归档 → 弃用
```

### 3.2 状态定义

| 状态 | 标记方式 | 含义 |
|------|---------|------|
| 草稿 | `状态: 草稿` | 编写中，不完整 |
| 评审中 | `状态: 评审中` | 完成待审核 |
| 正式 | `状态: 正式` | 已通过评审，可引用 |
| 维护中 | `状态: 维护中` | 仍在用但需更新 |
| 归档 | `状态: 归档` | 移至 `11-archive/` |
| 弃用 | `状态: 弃用 - 被 [新文档] 取代` | 不可引用 |

### 3.3 新建文档流程

```
确定类型/位置 → 使用模板 → 填写元数据 → 编写内容
       ↓
更新 README.md 和本层索引 → 标记"评审中" → 团队评审 → 标记"正式"
```

## 4. 版本管理规范

### 4.1 语义化版本号：`MAJOR.MINOR.PATCH`

| 层级 | 触发条件 |
|------|---------|
| MAJOR | 架构重构、需求重大调整 |
| MINOR | 新增模块、功能增强 |
| PATCH | 修正错误、补充说明 |

### 4.2 文档元数据模板

```markdown
# [文档标题]

> **版本**: X.Y.Z | **日期**: YYYY-MM-DD | **状态**: 正式
```

### 4.3 变更日志

```markdown
| 版本 | 日期 | 变更内容 | 变更人 |
```

## 5. 文档依赖关系管理

### 5.1 关系类型

| 类型 | 含义 | 元数据 |
|------|------|--------|
| 上游 | 本文档依赖的 | `上游文档: [xxx]` |
| 下游 | 依赖本文档的 | `下游文档: [xxx]` |
| 相关 | 关联但不依赖 | `相关文档: [xxx]` |

### 5.2 变更影响分析

| 变更文档 | 需同步更新 |
|----------|:-----------|
| `00-requirements/req-ok.md` | `02-architecture/ARCHITECTURE.md` → `08-tasks/TASK_BREAKDOWN.md` |
| `02-architecture/ARCHITECTURE.md` | `03-modules/*/DESIGN.md` → `07-adr/*` |
| ADR | `07-adr/README.md` → `DOCUMENT_RELATIONSHIP.md` |
| 模块 DESIGN.md | `ARCHITECTURE.md` → 相关 ADR |

## 6. 文档归档机制

### 6.1 归档触发条件

- 被新文档完全取代
- 相关功能已移除
- 超过 6 个月未更新且不再使用

### 6.2 归档流程

```
确认归档 → 更新状态为"归档" → 添加替代文档链接
       ↓
移至 11-archive/ → 更新 README 索引
```

### 6.3 归档目录

```
11-archive/
├── specs/          # 已完成的特性规格（7个子规格）
└── legacy_code/    # 旧代码（dialog/web）
```

## 8. 文档完整性检查清单

### 8.1 每次提交前

- [ ] 文档元数据完整（版本、日期、状态）
- [ ] 相关层 README.md 索引已更新
- [ ] 变更日志已记录
- [ ] 下游文档是否需要同步

### 8.2 周度检查

- [ ] 评审中文档是否有进展
- [ ] 维护中文档是否需要更新
- [ ] 是否有可归档文档

### 8.3 月度检查

- [ ] 文档关系图路径是否有效（所有 `../` 相对路径）
- [ ] ADR 编号是否连续无冲突
- [ ] 是否有版本冲突风险
- [ ] `req-ok.md` 和 `ARCHITECTURE.md` 是否一致

## 9. 最佳实践

### DOs
✅ 每个文档明确负责人
✅ 变更时检查下游文档并同步更新
✅ 使用相对路径引用（防止目录移动后断裂）
✅ 定期归档废弃文档
✅ 新增文档后更新对应层的 README.md

### DON'Ts
❌ 不创建无人负责的文档
❌ 不让文档状态长期停在"草稿"
❌ 不直接删除文档（应归档 → `11-archive/`）
❌ 不在多处重复维护相同信息
❌ 不让需求文档与架构文档产生不一致
