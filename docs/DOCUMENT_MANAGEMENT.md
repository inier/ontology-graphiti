# 文档管理规范

> **版本**: 1.0.0 | **日期**: 2026-05-03 | **状态**: 正式
> **用途**: 确保文档体系一致性、避免版本冲突、建立变更追踪机制

---

## 1. 文档体系总览

### 1.1 文档分类与职责

| 文档类型 | 存储位置 | 负责人 | 版本管理 |
|---------|---------|--------|---------|
| **战略层文档** | `docs/` (根目录) | 架构师/产品 | 版本号 + 日期 |
| **架构层文档** | `docs/ARCHITECTURE.md` | 架构师 | 版本号 + 日期 |
| **决策层文档** | `docs/adr/` | 架构师 | ADR-xxx 编号 |
| **模块层文档** | `docs/modules/*/DESIGN.md` | 模块负责人 | 版本号 |
| **UI设计层** | `docs/ui/` | 设计师 | 版本号 |
| **特性规格** | `.trae/specs/*/` | 特性负责人 | Git 版本 |
| **工作记忆** | `.workbuddy/memory/` | 团队 | 日期命名 |
| **实现对比** | `.trae/documents/` | 开发者 | Git 版本 |

### 1.2 权威文档清单（唯一真相来源）

| 文档 | 路径 | 更新频率 |
|------|------|---------|
| 需求定稿 | `docs/req-ok.md` | 仅重大变更 |
| 核心架构 | `docs/ARCHITECTURE.md` | 架构调整时 |
| ADR 索引 | `docs/adr/README.md` | 新增 ADR 时 |
| 文档关系图 | `docs/DOCUMENT_RELATIONSHIP.md` | 体系调整时 |
| **本文档** | `docs/DOCUMENT_MANAGEMENT.md` | 机制调整时 |

## 2. 文档生命周期管理

### 2.1 文档状态流转

```
草稿 → 评审中 → 正式 → 维护中 → 归档 → 弃用
  ↓        ↓        ↓       ↓
待完善   待审核   可引用   可更新
```

### 2.2 文档状态定义

| 状态 | 说明 | 标记方式 |
|------|------|---------|
| **草稿 (Draft)** | 正在编写，内容不完整 | `> **状态**: 草稿` |
| **评审中 (Review)** | 内容完成，待团队评审 | `> **状态**: 评审中` |
| **正式 (Active)** | 已通过评审，可作为权威引用 | `> **状态**: 正式` |
| **维护中 (Maintenance)** | 仍在使用，但需要更新 | `> **状态**: 维护中` |
| **归档 (Archived)** | 历史参考，不再更新 | `> **状态**: 归档`，移动到 `docs/archive/` |
| **弃用 (Deprecated)** | 已被新文档取代，不应再引用 | `> **状态**: 弃用 - 被 [新文档](xxx.md) 取代` |

### 2.3 新建文档流程

```
1. 确定文档类型和位置
   ↓
2. 使用对应模板创建
   ↓
3. 填写元数据（版本、日期、状态）
   ↓
4. 编写内容
   ↓
5. 更新相关索引文档
   ↓
6. 标记状态为"评审中"
   ↓
7. 团队评审
   ↓
8. 标记状态为"正式"
```

## 3. 版本管理规范

### 3.1 版本号格式

采用语义化版本号：`MAJOR.MINOR.PATCH`

| 层级 | 说明 | 更新场景 |
|------|------|---------|
| **MAJOR** | 重大变更 | 架构重构、需求重大调整 |
| **MINOR** | 次要变更 | 新增模块、功能增强 |
| **PATCH** | 补丁 | 修正错误、补充说明 |

### 3.2 文档元数据规范

所有文档必须包含以下元数据头部：

```markdown
# [文档标题]

> **版本**: X.Y.Z | **日期**: YYYY-MM-DD | **状态**: [状态]
> **作者**: [负责人] | **最后更新**: YYYY-MM-DD
> **相关文档**: [关联文档链接]
> **替代文档**: [如已弃用，列出替代文档]
```

### 3.3 变更日志

每个正式文档应包含变更日志章节：

```markdown
## 变更日志

| 版本 | 日期 | 变更内容 | 变更人 |
|------|------|---------|--------|
| 1.1.0 | 2026-04-20 | 新增模块设计章节 | 张三 |
| 1.0.0 | 2026-04-15 | 初始版本 | 李四 |
```

## 4. 文档依赖关系管理

### 4.1 依赖关系定义

| 关系类型 | 说明 | 标记方式 |
|---------|------|---------|
| **上游 (Upstream)** | 本文档依赖的文档 | `> **上游文档**: [xxx](xxx.md)` |
| **下游 (Downstream)** | 依赖本文档的文档 | `> **下游文档**: [xxx](xxx.md)` |
| **相关 (Related)** | 相关但非依赖关系 | `> **相关文档**: [xxx](xxx.md)` |

### 4.2 变更影响分析

当变更一个文档时，必须检查并更新其下游文档：

| 文档变更 | 需要同步更新的文档 |
|---------|------------------|
| `req-ok.md` | `ARCHITECTURE_PLAN.md` → `ARCHITECTURE.md` → `TASK_BREAKDOWN.md` |
| `ARCHITECTURE.md` | `docs/modules/*/DESIGN.md` → `docs/adr/*` |
| ADR 文档 | `docs/adr/README.md` → `DOCUMENT_RELATIONSHIP.md` |
| 模块设计 | `ARCHITECTURE.md` → 相关 ADR |

### 4.3 依赖关系图

参考 `docs/DOCUMENT_RELATIONSHIP.md` 维护完整的文档关系图。

## 5. 特性规格文档管理（.trae/specs/）

### 5.1 规格文档目录结构

```
.trae/specs/
└── [feature-name]/
    ├── spec.md           # 特性规格说明
    ├── tasks.md          # 任务拆解清单
    ├── checklist.md      # 验收检查清单
    └── archive/          # 旧版本归档
```

### 5.2 spec.md 模板

```markdown
# [特性名称] 规格

> **版本**: 1.0.0 | **日期**: YYYY-MM-DD | **状态**: 正式
> **负责人**: [姓名]
> **上游文档**: [关联架构/需求文档]
> **影响范围**: [受影响的模块]

## 为什么 (Why)

## 变更内容 (What)

## 影响分析 (Impact)

## 新增需求 (Added Requirements)

## 修改需求 (Modified Requirements)

## 删除需求 (Removed Requirements)

## 设计原则

## 交付物
```

### 5.3 特性规格生命周期

```
需求提出 → spec.md 创建 → 评审 → tasks.md 细化 → 执行 → 验证 → 完成 → 归档
```

## 6. 工作记忆管理（.workbuddy/memory/）

### 6.1 记忆文档用途

- 记录开发过程中的临时决策
- 保存会议纪要
- 记录问题排查过程
- 临时知识沉淀

### 6.2 记忆文档规范

- 命名格式：`YYYY-MM-DD_[主题].md`
- 状态标记：如果内容已沉淀到正式文档，标记为 `> **状态**: 已沉淀`
- 定期清理：每月回顾，将有用内容迁移到正式文档

## 7. 文档清理与归档机制

### 7.1 归档触发条件

- 文档被新文档完全取代
- 相关功能已移除
- 超过 6 个月未更新且不再使用

### 7.2 归档流程

```
1. 确认文档可以归档
   ↓
2. 更新文档状态为"归档"
   ↓
3. 添加归档说明和替代文档链接
   ↓
4. 移动到 `docs/archive/` 对应子目录
   ↓
5. 更新相关索引，标记为归档状态
```

### 7.3 归档目录结构

```
docs/archive/
├── architecture/    # 旧架构文档
├── adr/            # 已弃用的 ADR
├── specs/          # 已完成的特性规格
└── ui/             # 旧 UI 设计
```

## 8. 文档完整性检查清单

### 8.1 日常检查（每次提交前）

- [ ] 文档元数据是否完整（版本、日期、状态、作者）
- [ ] 相关索引是否已更新
- [ ] 变更日志是否已记录
- [ ] 下游文档是否需要同步

### 8.2 周度检查

- [ ] 评审中状态的文档是否有进展
- [ ] 维护中状态的文档是否需要更新
- [ ] 是否有文档可以归档

### 8.3 月度检查

- [ ] 工作记忆文档是否需要清理和沉淀
- [ ] 文档关系图是否需要更新
- [ ] 是否有版本冲突风险

## 10. 最佳实践

### 10.1 DOs

✅ 每个文档都有明确的负责人  
✅ 及时更新文档元数据和变更日志  
✅ 变更文档时检查并更新下游文档  
✅ 定期清理归档不再使用的文档  
✅ 使用相对路径引用其他文档  

### 10.2 DON'Ts

❌ 不要创建没有负责人的文档  
❌ 不要让文档状态长期停留在"草稿"或"评审中"  
❌ 不要直接修改"正式"状态的文档，应走变更流程  
❌ 不要删除有价值的历史文档，应归档处理  
❌ 不要在多个地方维护相同信息，避免信息不同步
