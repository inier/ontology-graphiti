# Feature Specification: 微服务架构拆分可行性评估

**Feature Branch**: `004-microservice-split`

**Created**: 2026-06-11

**Status**: Draft

**Input**: User description: "评估微服务架构的可行性，将数据采集和处理/本体设计/本体应用等按独立性拆分"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 评估微服务拆分边界与可行性 (Priority: P1)

架构师需要评估当前 ODAP 单体应用拆分为独立微服务的可行性，明确三大领域（数据采集与处理、本体设计、本体应用）的边界、依赖关系和拆分策略。评估结果需包含每个候选微服务的独立性度量、耦合点识别、数据流分析，以及拆分后的收益与风险对比，为决策层提供可量化的拆分依据。

**Why this priority**: 可行性评估是所有后续拆分工作的前提，没有清晰的边界定义和可行性判断，任何拆分行动都可能造成系统不稳定或过度拆分。

**Independent Test**: 可通过完成一份包含耦合度评分、数据流图、收益风险矩阵的评估报告来独立测试，报告需覆盖三大领域的所有模块。

**Acceptance Scenarios**:

1. **Given** 当前 ODAP 单体架构（7大业务领域、30+ 路由模块）, **When** 架构师执行微服务拆分评估, **Then** 系统输出三大领域的模块归属映射，每个模块明确归属且无歧义
2. **Given** 模块归属映射已完成, **When** 分析跨领域依赖, **Then** 识别出所有跨领域调用链并量化耦合度（0-10 分），标记高耦合点（≥7 分）
3. **Given** 耦合分析完成, **When** 评估各领域独立性, **Then** 每个候选微服务获得独立性评分，独立性低于阈值的领域标记为"不建议独立部署"
4. **Given** 评估完成, **When** 生成可行性报告, **Then** 报告包含明确的"建议拆分/建议保留/需进一步分析"三类结论

---

### User Story 2 - 数据采集与处理微服务独立运行 (Priority: P2)

数据工程师希望数据采集与处理模块能够独立部署和扩展，不受本体设计或本体应用模块的影响。当数据摄入量激增时，只需扩容数据采集服务，无需扩容整个单体应用。数据采集服务需独立管理数据源连接、文档解析（PDF/Word/OCR）、批量导入、新闻抓取、Web 爬虫等能力，并通过标准接口向其他服务提供已处理的结构化数据。

**Why this priority**: 数据采集是系统的入口层，流量波动大、扩展需求频繁，独立部署的收益最直接，但依赖本体定义进行数据验证，需要先明确接口契约。

**Independent Test**: 可通过停止本体设计和本体应用服务，仅启动数据采集服务，验证数据采集、解析、存储功能正常运行来独立测试。

**Acceptance Scenarios**:

1. **Given** 数据采集服务独立部署, **When** 用户上传包含 50 条实例的 CSV 文件, **Then** 系统完成数据解析和验证，结构化数据通过标准接口可被其他服务消费
2. **Given** 数据采集服务独立运行, **When** 本体设计服务不可用, **Then** 数据采集服务仍可完成数据摄入，待本体设计服务恢复后自动进行数据验证
3. **Given** 数据采集量激增, **When** 运维人员扩容数据采集服务实例, **Then** 采集吞吐量线性增长，不影响本体设计和本体应用服务的性能
4. **Given** 数据采集服务处理 PDF/Word/网页等异构数据, **When** 执行文档解析, **Then** 解析结果以统一格式输出，下游服务无需关心原始数据格式

---

### User Story 3 - 本体设计微服务独立运行 (Priority: P2)

领域专家希望本体设计模块能够独立运行，专注于本体模型定义、版本管理、验证引擎、分支合并等核心能力。本体设计服务不依赖数据采集服务的运行状态，也不依赖本体应用服务的在线情况。当本体设计服务更新本体定义后，通过事件通知机制告知下游服务。

**Why this priority**: 本体设计是平台的核心知识资产，变更频率低但影响面大，独立部署可保证定义变更的稳定性和可追溯性，同时避免被其他模块的负载波动影响。

**Independent Test**: 可通过停止数据采集和本体应用服务，仅启动本体设计服务，验证本体 CRUD、版本管理、验证引擎功能正常运行来独立测试。

**Acceptance Scenarios**:

1. **Given** 本体设计服务独立部署, **When** 领域专家创建包含 3 种实体类型和 2 种关系的本体, **Then** 本体定义保存成功，版本记录自动生成
2. **Given** 本体设计服务独立运行, **When** 数据采集服务不可用, **Then** 本体设计服务仍可完成本体定义、版本回滚、分支合并等操作
3. **Given** 本体定义发生变更, **When** 新版本发布, **Then** 通过事件通知机制告知数据采集服务和本体应用服务，下游服务可按需响应
4. **Given** 本体设计服务包含验证引擎, **When** 提交不合规的本体定义, **Then** 验证引擎拒绝提交并返回具体违规原因

---

### User Story 4 - 本体应用微服务独立运行 (Priority: P3)

应用开发者希望本体应用模块（包括运行时引擎、状态机、蓝图设计器、服务化、Team Agent、查询 API 等）能够独立部署。本体应用服务消费本体设计服务提供的本体定义，执行运行时逻辑、状态传播、动作触发等应用层能力，不依赖本体设计服务的实时在线。

**Why this priority**: 本体应用是面向终端用户的核心交互层，功能模块最多、复杂度最高，独立部署可提升用户体验和系统弹性，但依赖本体定义数据，拆分难度最大。

**Independent Test**: 可通过停止数据采集和本体设计服务，使用缓存的本体定义数据，验证运行时引擎、状态机、查询 API 功能正常运行来独立测试。

**Acceptance Scenarios**:

1. **Given** 本体应用服务独立部署, **When** 用户通过查询 API 查询本体数据, **Then** 查询结果正确返回，响应时间不劣于单体架构
2. **Given** 本体应用服务独立运行, **When** 本体设计服务暂时不可用, **Then** 本体应用服务使用缓存的本体定义继续运行，已加载的运行时实例不受影响
3. **Given** 本体应用服务包含运行时引擎和状态机, **When** 触发状态变更事件, **Then** 状态传播和动作触发正确执行，行为与单体架构一致
4. **Given** 本体应用服务包含蓝图设计器, **When** 用户在蓝图设计器中编排本体节点, **Then** 编排结果正确保存并可恢复

---

### User Story 5 - 跨服务通信与数据一致性保障 (Priority: P2)

系统管理员需要确保三大微服务之间的通信可靠、数据一致。当本体定义变更时，数据采集服务和本体应用服务需及时感知；当数据采集完成时，本体应用服务需能获取最新数据。服务间通信需支持同步调用和异步事件两种模式，数据不一致时需有检测和修复机制。

**Why this priority**: 跨服务通信和数据一致性是微服务架构的核心挑战，直接决定拆分后系统的可用性和可靠性，与各服务独立运行同等重要。

**Independent Test**: 可通过模拟本体定义变更事件，验证数据采集服务和本体应用服务的事件接收和响应来独立测试。

**Acceptance Scenarios**:

1. **Given** 本体设计服务发布本体定义变更事件, **When** 事件发出, **Then** 数据采集服务和本体应用服务在 5 秒内收到事件通知
2. **Given** 服务间采用同步调用, **When** 被调用服务不可用, **Then** 调用方在超时后优雅降级，不导致级联故障
3. **Given** 服务间数据存在不一致, **When** 运行一致性检查, **Then** 系统识别不一致数据并提供修复建议
4. **Given** 某服务发生故障, **When** 故障恢复后, **Then** 该服务能自动同步缺失的事件和数据变更，恢复到一致状态

---

### Edge Cases

- 当三大领域存在循环依赖时（如本体应用服务需要回调本体设计服务进行验证），如何打破循环？
- 当数据采集服务处理的数据量远超本体设计服务的处理能力时，如何进行背压控制？
- 当本体定义在多个服务中存在缓存副本时，如何保证缓存的最终一致性？
- 当某个微服务完全不可用时，其他服务的降级策略是什么？用户可接受的数据丢失范围是多少？
- 当需要跨服务执行事务操作（如创建本体同时导入数据）时，如何保证原子性？
- 当服务拆分后，原有的 SQLite 存储层如何迁移？是否需要引入共享数据库或每个服务独立数据库？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供三大领域（数据采集与处理、本体设计、本体应用）的模块归属映射，明确每个现有模块的归属
- **FR-002**: 系统 MUST 识别并量化三大领域之间的所有跨领域依赖，包括直接调用、数据依赖、事件依赖
- **FR-003**: 系统 MUST 为每个候选微服务计算独立性评分，评分维度包括：代码独立性、数据独立性、部署独立性、团队独立性
- **FR-004**: 数据采集与处理微服务 MUST 独立完成数据摄入（CSV/PDF/Word/OCR/网页/新闻）、数据解析、数据验证功能
- **FR-005**: 本体设计微服务 MUST 独立完成本体 CRUD、版本管理、验证引擎、分支合并、继承解析功能
- **FR-006**: 本体应用微服务 MUST 独立完成运行时引擎、状态机、蓝图设计器、服务化部署、Team Agent、查询 API 功能
- **FR-007**: 各微服务 MUST 通过定义良好的接口契约通信，禁止跨服务直接访问对方存储层
- **FR-008**: 系统 MUST 提供服务间事件通知机制，支持本体定义变更、数据摄入完成等关键事件的异步传播
- **FR-009**: 系统 MUST 提供服务降级策略，当依赖服务不可用时，当前服务可降级运行而非完全不可用
- **FR-010**: 系统 MUST 提供数据一致性检测机制，能识别跨服务数据不一致并提供修复方案
- **FR-011**: 各微服务 MUST 支持独立部署和独立扩缩容，一个服务的扩缩容不影响其他服务
- **FR-012**: 系统 MUST 提供跨服务分布式追踪能力，支持从数据摄入到本体应用的完整链路追踪
- **FR-013**: 系统 MUST 保留现有的 OPA 策略治理能力，跨服务权限校验仍通过 OPA 统一执行
- **FR-014**: 系统 MUST 提供服务间认证机制，防止未授权的服务间调用
- **FR-015**: 拆分后的系统 MUST 保持与现有前端 API 的兼容性，前端无需感知后端服务拆分

### Key Entities

- **微服务边界（Service Boundary）**: 定义每个微服务的职责范围、包含的模块、暴露的接口
- **接口契约（Interface Contract）**: 微服务间通信的协议定义，包括同步 API 和异步事件格式
- **依赖关系（Dependency）**: 微服务间的调用关系，包括调用方向、调用频率、耦合度评分
- **独立性评分（Independence Score）**: 候选微服务在代码、数据、部署、团队四个维度的独立性量化指标
- **降级策略（Degradation Policy）**: 依赖服务不可用时的行为定义，包括功能降级范围和数据一致性保证级别
- **事件定义（Event Definition）**: 服务间异步通信的事件格式，包括事件类型、载荷结构、消费方列表
- **数据一致性规则（Consistency Rule）**: 跨服务数据一致性的校验规则和修复策略

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 三大领域的模块归属映射覆盖 100% 的现有业务模块，无遗漏、无歧义归属
- **SC-002**: 每个候选微服务的独立性评分可量化计算，评分结果可复现
- **SC-003**: 各微服务独立部署后，核心功能（数据摄入、本体 CRUD、运行时执行）的响应时间不劣于单体架构的 120%
- **SC-004**: 服务间通信延迟（同步调用）在正常负载下不超过 50ms
- **SC-005**: 事件通知从发布到消费的端到端延迟不超过 5 秒
- **SC-006**: 单个微服务故障时，其他服务的核心功能可用率不低于 95%
- **SC-007**: 跨服务数据不一致问题在 30 分钟内可被检测和修复
- **SC-008**: 拆分后前端 API 兼容性达到 100%，前端代码零修改
- **SC-009**: 各微服务可独立扩缩容，扩容后吞吐量线性增长（偏差不超过 15%）
- **SC-010**: 可行性评估报告提供明确的拆分建议，包含"建议拆分/建议保留/需进一步分析"三类结论及理由

## Assumptions

- 当前 ODAP 单体架构的 7 大业务领域（core/decision/integration/platform/data/simulation/management）是拆分评估的起点
- 三大领域划分（数据采集与处理、本体设计、本体应用）是用户指定的拆分维度，评估需基于此维度展开
- 拆分评估采用渐进式策略，优先拆分独立性最高的领域，而非一次性全量拆分
- 现有的 SQLite 存储层在拆分后可能需要迁移到独立数据库，具体方案在规划阶段确定
- 现有的 Podman 容器化部署方案可扩展为多容器编排，无需引入新的编排工具
- OPA 策略引擎和审计日志作为共享基础设施，不纳入微服务拆分范围
- 前端应用作为独立部署单元，不纳入本次微服务拆分范围
- 评估过程中发现的强耦合模块，如无法在当前阶段解耦，可标记为"共享模块"暂缓拆分
- 服务间通信默认采用 HTTP/REST 同步调用 + 事件总线异步通知的混合模式
- 现有的 JWT 认证机制可扩展为服务间认证，无需引入新的认证框架
