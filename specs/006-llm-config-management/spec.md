# Feature Specification: LLM 与 API 密钥配置管理

**Feature Branch**: `006-llm-config-management`

**Created**: 2026-06-14

**Status**: Draft

**Input**: User description: "将项目中使用到的各项大模型配置和组件调用的api key等，优化为专门的配置界面进行管理，前端修改后，可直接生效。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员通过界面配置 LLM 服务连接 (Priority: P1)

系统管理员需要为平台配置大模型服务连接参数（API Key、API 基地址、模型名称），无需登录服务器修改环境变量或重启容器，在配置界面修改后立即生效。

**Why this priority**: LLM 是平台最核心的外部依赖，当前 API Key 和模型配置分散在 15+ 个文件中且默认值不一致，是最大的配置管理痛点。解决此问题后，管理员可以快速切换 LLM 供应商和模型，无需代码变更。

**Independent Test**: 可以通过在配置界面修改 LLM API Key 和模型名称，然后发起一次问答请求来验证配置是否生效，无需依赖其他功能。

**Acceptance Scenarios**:

1. **Given** 管理员已登录且拥有 admin 角色, **When** 导航到系统设置页面并填写 LLM 服务的 API Key、API 基地址和模型名称后点击保存, **Then** 配置被持久化存储，后续所有 LLM 调用使用新配置，无需重启服务
2. **Given** 管理员已配置 LLM 服务, **When** 修改 API 基地址从供应商 A 切换到供应商 B 并保存, **Then** 新的 LLM 请求使用供应商 B 的地址，正在进行的请求不受影响
3. **Given** 管理员输入了无效的 API Key, **When** 点击"测试连接"按钮, **Then** 系统返回明确的错误提示（如"API Key 无效"或"连接超时"），配置不会被保存
4. **Given** 管理员未配置 API Key, **When** 系统启动或用户发起 LLM 请求, **Then** 系统返回明确的配置缺失提示，而非静默使用空 Key

---

### User Story 2 - 管理员统一管理所有外部服务连接 (Priority: P2)

系统管理员需要在一个统一的界面中管理所有外部服务的连接配置，包括 Neo4j 图数据库、MinIO 对象存储、OPA 策略引擎、Redis 缓存、搜索服务（Tavily/DuckDuckGo/SerpAPI）等，而非分散在不同配置文件中。

**Why this priority**: 统一管理所有外部服务配置是配置管理的完整性要求，但优先级低于核心 LLM 配置，因为其他服务配置变更频率较低。

**Independent Test**: 可以通过在配置界面修改 Neo4j 密码或 MinIO 端点，然后执行相关操作来验证配置是否生效。

**Acceptance Scenarios**:

1. **Given** 管理员已登录, **When** 导航到系统设置页面, **Then** 可以看到所有外部服务的配置状态（已配置/未配置/连接异常），按服务类别分组展示
2. **Given** 管理员修改了 Neo4j 密码, **When** 点击保存, **Then** 新的数据库连接使用新密码，图查询操作正常执行
3. **Given** 管理员配置了 Tavily API Key, **When** 用户执行新闻摄入操作, **Then** 系统使用 Tavily 进行搜索增强
4. **Given** 管理员清除了某个可选服务的配置, **When** 该服务被请求, **Then** 系统优雅降级，返回明确提示而非报错

---

### User Story 3 - 管理员查看配置变更历史与回滚 (Priority: P3)

管理员需要查看配置的变更历史记录，包括谁在什么时间修改了什么配置，并能够回滚到之前的配置版本。

**Why this priority**: 审计和回滚能力是生产环境的重要保障，但可以在基础配置管理功能稳定后再添加。

**Independent Test**: 可以通过修改配置、查看变更记录、执行回滚操作来独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员修改了 LLM 模型配置, **When** 保存成功, **Then** 变更记录中新增一条包含操作人、时间、变更前值、变更后值的记录
2. **Given** 配置变更导致服务异常, **When** 管理员在变更历史中选择上一版本并点击回滚, **Then** 配置恢复到上一版本的值，服务恢复正常
3. **Given** 管理员查看变更历史, **When** 按时间范围或服务类别筛选, **Then** 只显示符合条件的变更记录

---

### User Story 4 - 敏感配置的安全管理 (Priority: P2)

管理员在配置界面输入的 API Key 和密码等敏感信息需要被安全存储和展示，避免明文泄露。

**Why this priority**: 安全性是配置管理的基本要求，与 P2 的统一管理同等重要。

**Independent Test**: 可以通过检查界面展示、API 响应和存储文件来验证敏感信息是否被正确脱敏和加密。

**Acceptance Scenarios**:

1. **Given** 管理员已配置 API Key, **When** 在配置界面查看, **Then** API Key 以脱敏形式展示（如 `sk-****abcd`），仅最后 4 位可见
2. **Given** 管理员需要查看完整 API Key, **When** 点击"显示"按钮, **Then** 完整 Key 临时展示，几秒后自动恢复脱敏
3. **Given** 配置被持久化存储, **When** 检查存储文件, **Then** 敏感字段以加密形式存储，非明文
4. **Given** 非管理员用户访问配置接口, **When** 请求获取配置, **Then** 返回 403 禁止访问

---

### Edge Cases

- 管理员同时修改多个服务的配置并保存时，部分服务配置验证失败如何处理？——应整体回滚，不允许部分保存
- 配置保存后，正在使用旧配置的长时间运行请求如何处理？——已发出的请求继续使用旧配置完成，新请求使用新配置
- 配置存储服务（SQLite）不可用时，配置界面如何表现？——应显示明确的错误提示，并允许重试
- 并发修改同一配置项时如何处理？——后保存的覆盖先保存的，变更历史记录两次修改
- 首次使用时没有任何配置，界面如何引导？——显示配置向导，标记必填项，提供默认值建议

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一的配置管理界面，支持管理以下服务类别的配置项：
  - LLM 服务（API Key、API 基地址、模型名称、温度参数）
  - 图数据库（URI、用户名、密码）
  - 对象存储（端点、访问密钥、密钥、是否 HTTPS）
  - 搜索服务（Tavily API Key、DuckDuckGo URL、SerpAPI Key）
  - 策略引擎（OPA URL）
  - 缓存服务（Redis URL）
  - 认证服务（JWT 密钥、算法、过期时间）
  - 通用设置（CORS 白名单、日志级别）

- **FR-002**: 系统 MUST 提供配置验证功能，在保存前测试外部服务连接是否可用，验证失败时不保存配置

- **FR-003**: 系统 MUST 在配置保存后立即生效，无需重启服务进程或容器

- **FR-004**: 系统 MUST 对敏感配置（API Key、密码、密钥）进行脱敏展示和加密存储

- **FR-005**: 系统 MUST 限制仅 admin 角色可访问配置管理功能，非管理员访问返回 403

- **FR-006**: 系统 MUST 记录配置变更历史，包含操作人、时间、变更前值、变更后值

- **FR-007**: 系统 MUST 支持配置回滚，管理员可选择历史版本恢复配置

- **FR-008**: 系统 MUST 统一 LLM 配置读取入口，消除当前 15+ 个文件中独立读取 OPENAI_API_KEY/OPENAI_API_BASE/OPENAI_MODEL 且默认值不一致的问题

- **FR-009**: 系统 MUST 在配置缺失时提供明确的错误提示，而非静默使用空值或占位值

- **FR-010**: 系统 MUST 支持配置分组展示，按服务类别组织配置项，每组可折叠展开

- **FR-011**: 系统 MUST 提供配置状态总览，显示各服务的连接状态（已配置/未配置/连接异常）

- **FR-012**: 系统 MUST 支持配置导入导出（敏感字段脱敏导出），便于环境迁移

### Key Entities

- **ServiceConfig**: 外部服务配置，包含服务类别（LLM/数据库/搜索/策略/缓存/存储/认证）、配置项列表、连接状态、最后验证时间
- **ConfigItem**: 单个配置项，包含键名、值（加密存储）、值类型（string/integer/boolean/url/password）、是否敏感、是否必填、默认值、描述、验证规则
- **ConfigRevision**: 配置变更记录，包含修订号、操作人、变更时间、变更项列表（含变更前值和变更后值）
- **ConfigValidationResult**: 配置验证结果，包含服务名称、是否通过、错误信息、响应时间

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可以在 2 分钟内完成任意一个外部服务的配置变更，且变更在保存后 5 秒内生效
- **SC-002**: 所有 LLM 调用统一从配置管理服务读取 API Key 和模型参数，零处硬编码或独立读取
- **SC-003**: 敏感配置在界面展示和 API 响应中 100% 脱敏，存储中 100% 加密
- **SC-004**: 配置变更 100% 有审计记录，记录包含完整的变更前后值
- **SC-005**: 非管理员用户访问配置接口时 100% 返回 403
- **SC-006**: 配置验证功能在 10 秒内返回结果，超时视为验证失败

## Assumptions

- 配置存储使用 SQLite 持久化，与项目现有存储模式一致
- 配置热更新通过内存缓存 + 通知机制实现，不依赖外部配置中心
- 敏感字段加密使用 AES-256 或项目已有的加密方案，密钥从环境变量读取
- 配置管理 API 仅在 admin 角色下可用，通过现有 JWT 认证体系保护
- 前端配置页面放在"系统设置"模块下，路由为 `/settings`
- 配置导入导出功能中，敏感字段导出时替换为占位符，导入时跳过占位符字段
- 配置回滚通过变更历史记录实现，不保留完整配置快照
- 当前 `config_composer.py` 的 5 层配置体系将被激活和扩展，作为配置管理的后端基础
